# MV3 扩展调试、权限审查、打包与发布

扩展能够在开发者模式加载，只说明清单和文件至少能被浏览器接受，不代表后台休眠后仍可靠、权限与功能匹配，也不代表商店审查一定通过。交付需要把可复现验收、包内容、版本升级和数据说明一起检查，本章以标题笔记工具为对象建立流程。

## 前置条件与交付边界

先完成[消息、Storage 与完整交互](/tutorials/browser-extensions/implementation.html)，本章继续使用桌面 Chrome 120 及以上的 MV3 示例。准备一个独立扩展目录、本地演示页和可访问的文件管理工具。命令使用 Bash；打包示例需要本机已有 zip 与 unzip，没有时先检查，不擅自安装依赖。

本章不注册账号、不购买开发者资格、不上传商店、不执行真实发布，也不把应用商店政策描述为永久不变。提交之前应重新核对 Chrome 官方政策和控制台要求，审核、价格、表单与截图要求可能调整。教程可以解释边界，不能替代你的组织授权。

交付对象应明确是源文件、候选 ZIP 包还是已发布版本。标题笔记示例仍是教学工具，未实现跨窗口强并发、加密存储或完整无障碍审计；这些限制要如实写在交付说明，不因为功能小就省略隐私说明。

## 三个执行上下文的调试入口

内容脚本在网页上下文附近运行，页面 DevTools 里需要选择对应扩展执行环境。popup 是独立扩展页面，打开时可以右键检查；关闭 popup 通常销毁该界面。后台在扩展管理页的 Service Worker 检查入口观察，停止和重新唤醒也在这里确认。

一个 Console 没有错误，不代表其他上下文没有错误。popup 发消息失败可能来自 worker 未注册、注入失败、目标导航或内容脚本响应缺失。按“界面发出请求 → 后台接受 → 注入完成 → 页面响应 → 存储完成 → UI 展示”的顺序定位，比到处加日志更有用。

日志应使用短操作标识、结果状态和错误类别，不写完整页面文本、URL 参数、Cookie 或 storage 内容。需要跨上下文串联时可为一次请求生成标识，最终版应评估是否仍需保留。不要把开发日志变成默认数据收集通道。

修改 `manifest.json` 后重新加载扩展，修改内容脚本后也刷新目标页，防止旧注入上下文残留。重载可能导致旧内容脚本的 runtime 上下文失效，这在开发流程中常见，不应为隐藏提示而无限重试。先确认浏览器当前实际使用哪份目录与版本。

```js
const manifest = chrome.runtime.getManifest();
console.log({
  name: manifest.name,
  version: manifest.version,
  manifestVersion: manifest.manifest_version
});
```

在后台或 popup Console 运行，预期名称、版本和清单版本与候选文件一致。扩展 ID 可帮助区分两份同时加载的实验，但不要把开发模式 ID 当作商店最终身份承诺。两个不同 ID 的扩展有不同存储区域，不能用另一份实例的记录证明升级保留成功。

## 生命周期与验收矩阵

先关闭后台 DevTools 再测试休眠与唤醒，因为检查窗口可能改变后台生命周期。不要使用固定等待秒数作为唯一证据；在扩展管理页观察 worker 状态，然后重新打开 popup 请求记录。成功应来自 `storage.local` 读取，而不是旧变量还活着。

以下矩阵给出标题笔记的可观察标准，并非已经运行的结果：

| 场景 | 操作 | 应观察的结果 |
| --- | --- | --- |
| 首次安装 | 打开 popup | 无保存记录，按钮可用 |
| 正常采集 | 在三标题本地页点击采集 | 总数 3，展示对应文本 |
| 重复操作 | 同一页采集三次 | 一份最新快照，不累积重复监听 |
| 页面刷新 | 刷新后重新采集 | 新内容脚本可响应 |
| 后台停止 | 关闭调试工具后重新读取 | 已保存快照可恢复 |
| 受保护页面 | 在浏览器内部页采集 | 明确失败，不伪装零标题 |
| 清除 | 清除后关闭并重开 popup | 无记录 |
| 上限 | 页面超过 50 个非空标题 | 列表最多 50，总数不截断 |

还应检查键盘焦点、按钮禁用时反馈、长标题换行、空标题、目标标签关闭以及窗口切换。`lastFocusedWindow` 查询得到的目标可能随用户操作变化，因此真正产品需要明确“当前页”的时间点。对复杂工具可在请求中绑定目标并在后续校验，避免用户误以为操作了另一页。

并发是独立边界：两个 popup 同时采集时，示例最后完成写入的记录生效；清除和另一采集竞争可能重新产生记录。交付前要决定接受并说明这种语义，还是增加操作序列与持久版本检查。不能把单窗口按钮禁用等同于全扩展互斥。

记录每项实际状态为通过、失败或未验证，失败要附步骤与错误位置。没有运行过的旧浏览器、企业管理环境和衍生浏览器都属于未验证范围，不写“全平台兼容”。本章最低版本限定的是代码契约，不是完整测试覆盖承诺。

## 权限、资源与消息安全审查

清单审查从功能倒推：activeTab 对应用户主动采集，scripting 对应内容脚本注入，storage 对应最近记录。没有自动全站采集，因此无需通配主机授权；没有读取浏览历史，因此无需 history；没有 Cookie 访问，因此不申请 cookies。减少权限既降低风险，也让用户更容易理解功能。

若未来功能只对特定站点长期运行，应限定 host 范围并说明目的。可选权限必须由明确用户操作请求，拒绝授权时应有可用的降级状态，而不是一直弹提示。权限扩大可能引发用户警告、重新授权或商店审查，不能悄悄混入一次普通更新。

后台消息只接受预期来源与已知类型，并校验数据。不要实现“收到任意 URL 就 fetch，再把结果返回”的高权限代理，也不要接受页面发来的代码字符串执行。`externally_connectable` 只在真正需要外部网站或扩展通信时声明，且需要单独的来源与操作限制。

`web_accessible_resources` 让指定资源可被匹配的网站访问，不是为了文件都能找到而列出整个包。扩展内部 popup 脚本和后台文件通常不需要全部暴露。内容脚本能引用包内注入文件，也不意味着网页本身应该有读取这些资源的权限。

MV3 通常要求可执行逻辑随扩展包提供，不通过远程脚本、eval 或动态函数构造绕过审核。远程 JSON 作为配置仍应明确字段、大小和用途，不能把字符串解释成新逻辑。CSP 是执行边界的一部分，不应该为了让错误代码运行而放宽到任意源。

本例标题用 textContent 呈现，storage 没有凭据，错误日志不含正文。仍需阅读所有包文件，检查意外第三方请求和过度收集。浏览器 API 的授权不能替代用户对数据用途的知情同意，商店描述也必须与代码实际行为一致。

## 数据版本、升级与清除

上一章记录包含 `schemaVersion: 1`。发布后数据会与代码版本共同演化，不能因为清单版本从 0.2.0 变到 0.3.0，就假定旧数据已经迁移。先验证旧格式，转换到新结构，再持久化；失败时保留旧数据或明确提示，不静默清空用户记录。

`runtime.onInstalled` 会在首次安装、更新及一些浏览器更新情形触发，处理时查看 `details.reason`，不把所有触发当首次安装。后台监听器仍需顶层注册。升级逻辑应可重复或能够检测完成状态，避免一次中断导致下次误判已处理。

不涉及结构变化的版本可仅更新说明与代码。下面只是可放在未来后台中的事件区分示例，不要用它替换已有完整消息实现：

```js
chrome.runtime.onInstalled.addListener((details) => {
  if (details.reason === "install") {
    console.info("Fresh installation; no existing snapshot is required.");
  } else if (details.reason === "update") {
    console.info("Update detected; validate stored schema before use.");
  }
});
```

这个示例没有实际迁移，不能把日志当迁移成功。真实迁移要有旧数据样本、转换预期和失败回退验证。重新加载或更新同一个已安装实例通常与卸载重装不同；卸载一般会移除该扩展的 local 数据，sync 和外部服务还有另外生命周期，应逐项说明。

清除按钮只移除本扩展指定键，不应清理其他扩展、整个浏览器或所有网站数据。如果用户期望“删除全部本工具数据”，应确认还有没有其他本地键、sync、IndexedDB 或远端记录。默认的 `storage.local` 也受配额限制，数据多时应该按业务限制或淘汰策略管理，而不是立即申请 unlimitedStorage。

## 生成最小候选包并核对内容

候选包只包含扩展运行所需文件，ZIP 根目录应直接是 `manifest.json`，不要把外层项目文件夹一起套进去。`.git`、测试日志、真实样本、环境文件、服务器脚本和教学页面都不应自动进入扩展包。本例没有构建步骤，因此可以显式列出五个源文件。

在准备好的 `heading-notebook` 目录内运行以下命令。脚本先检查工具与清单解析，输出到全新临时目录，不覆盖任何已有包：

```bash
command -v zip
command -v unzip
node -e 'const fs=require("node:fs"); const m=JSON.parse(fs.readFileSync("manifest.json","utf8")); if(m.manifest_version!==3) process.exit(2); console.log(m.name,m.version);'
out=$(mktemp -d)
zip "$out/heading-notebook.zip" \
  manifest.json background.js content.js popup.html popup.js
unzip -l "$out/heading-notebook.zip"
printf 'Candidate package: %s\n' "$out/heading-notebook.zip"
```

预期列表只有这五个文件，且 `manifest.json` 位于根目录。JSON 能解析不代表字段语义有效，还要在 Chrome 加载检查。包列表能证明包含哪些文件，不能证明没有恶意逻辑；内容审查和运行验收仍必不可少。

可进一步将候选 ZIP 解压到另一个新临时目录，并从那里加载已解压扩展，验证“实际交付包”而不只是原源码目录。检查文件路径大小写、引用是否齐全、是否依赖源目录之外的资源。操作前确认解压目标为空，不覆盖原工作目录。

本地“打包扩展程序”生成的 CRX/私钥与商店 ZIP 上传不是同一流程。私钥影响扩展身份，应按机密处理，不上传仓库、不发公开日志。普通用户安装 CRX 也受平台政策约束，不能保证双击就可安装；企业部署与商店分发应使用各自官方流程。

## 商店提交、反馈与回滚边界

提交前按官方控制台要求准备描述、截图、单一用途说明、权限理由和隐私披露。声明“不收集数据”前先区分本地处理、设备外传输、日志和第三方服务，按实际代码与商店定义填写。没有远程服务不代表无需解释页面数据访问。

上传候选包、填写表单和最终发布都是外部写操作，应经有权限的人确认。审核时间和结论不能保证，未提交就标记未提交，待审核就标记待审核。不要在教程或交付记录中编造“审核已通过”或固定耗时。

发布后观察崩溃与用户反馈时也要限制数据收集，不能为了诊断默认上传标题正文。修复版本应增加允许格式的扩展版本号，旧 ZIP 不能简单当成普遍可行的降级通道；商店版本通常要求向前推进。回滚可以是发布一个更高版本但恢复旧逻辑，数据结构是否向后兼容必须另行验证。

发现高风险权限或数据泄漏时，优先停止传播并启动事故流程，而不是只在下一版改描述。用户是否能停用、清除记录、了解变更，是工具长期可信的重要部分。演示代码不提供完整运营系统，交付说明必须保留这些范围限制。

## 练习与完成标准

练习把实际候选包从新目录加载，按验收矩阵记录每项结果；故意移除 popup.js 的候选副本，确认错误能定位，随后只在副本修复。新增普通标题、长标题和空标题，检验上限及纯文本呈现。不要用真实敏感页面做安全测试。

再写一份简短交付记录，包含扩展版本、Chrome 测试版本、权限与理由、包文件清单、数据保存位置、已验证项目和未验证范围。只做本地演示就明确商店未提交；只静态审查就明确运行未验证。记录应描述结果，不把“看起来没问题”当检查标准。

完成标准是源码、清单、包内容和描述一致，关键上下文都能定位错误，冷启动和清除有证据，升级与并发边界明确，发布权限得到确认。可返回[教程目录](/tutorials/)回顾整组内容，并用同样的证据习惯处理更复杂扩展。
