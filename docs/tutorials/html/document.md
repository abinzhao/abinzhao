# HTML 语义文档与资源加载：构建可阅读的页面

HTML 首先是一份描述内容关系的文档，而不是摆放像素的工具。浏览器把源代码解析成节点树，CSS 决定节点如何显示，JavaScript 决定节点如何响应操作。三者分工越清楚，页面越容易阅读、维护和适配辅助技术。本篇用一份学习笔记页面说明这种分工，并解释文档结构、语义选择和资源加载为什么会影响实际体验。

## 前置知识与适用范围

你只需要会创建文本文件、保存文件以及打开浏览器，无须先学习框架。准备一个独立的练习目录，入口文件名为 `index.html`，编码使用 UTF-8。本文采用 HTML Living Standard 中长期使用的基础元素，适用于常见现代浏览器，不声称覆盖某个最新版本。不同浏览器的默认字体、控件外观和开发者工具名称可能不同，但本文依赖的文档语义一致。

本篇的静态示例可以直接打开本地文件。后续如果使用模块脚本、请求接口或测试 HTTP 缓存，则应通过本地 HTTP 服务访问；文件协议与 HTTP 协议的安全规则不同，不能把文件协议下的失败直接归因于 HTML。练习不需要安装第三方依赖，也不会发送个人信息。

## 文档树为什么比外观更重要

浏览器读到开始标签时创建元素，读到文本时创建文本节点，再根据嵌套关系形成 DOM。源代码中缩进只是帮助人阅读，并不决定父子关系。结束标签、元素允许的内容和解析规则才决定实际树形结构。浏览器遇到不合法嵌套时可能自动修复，因此“页面看起来正常”不是结构正确的证据。检查开发者工具中的元素树，才能看到解析后的真实结果。

语义元素说明内容用途：`nav` 表示主要导航，`main` 表示页面主体，`article` 表示可以独立理解的内容，`section` 表示有主题的分区。它们不天然提供某种卡片样式。只需要一层布局容器、没有特别内容含义时使用 `div` 更准确。把所有容器都换成 `section` 并不会自动提升可访问性，反而可能增加没有标题的模糊分区。

标题表达层级而不是字号。主标题使用 `h1`，其下的主题使用 `h2`，再下一级使用 `h3`。本文示例只有一个清晰的页面主标题，这是一种容易理解的组织方式，并不是声称规范绝对禁止多个一级标题。不要为了得到较小字体跳过标题层级；外观应由 CSS 控制。浏览器、搜索工具和屏幕阅读器都可以利用标题关系帮助读者定位信息。

`head` 提供文档元信息，`body` 提供用户看到的内容。字符集声明应尽早出现，否则浏览器可能用错误编码解释中文。页面标题会出现在标签页和历史记录中，语言属性帮助辅助技术选择发音方式。视口声明让移动浏览器按设备宽度布局，但它不会自动解决内容过宽的问题。

## 第一步：创建完整的语义页面

在 `index.html` 中写入下面的全部代码，然后用浏览器打开该文件。这里的导航链接都是当前页面锚点，不依赖其他页面或网络资源。页内链接通过唯一的 `id` 找到目标，给每个目标起稳定名称比依赖节点在页面中的位置更可靠。

```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>周末学习笔记</title>
    <meta name="description" content="记录语义 HTML 的学习目标与实践结果。">
    <link rel="stylesheet" href="./styles.css">
    <script src="./main.js" defer></script>
  </head>
  <body>
    <header>
      <p>前端练习室</p>
      <nav aria-label="本页导航">
        <a href="#goals">学习目标</a>
        <a href="#notes">实践记录</a>
      </nav>
    </header>
    <main id="content">
      <h1>周末学习笔记</h1>
      <p>把内容关系写清楚，再逐步改善页面外观。</p>
      <section id="goals" aria-labelledby="goals-title">
        <h2 id="goals-title">学习目标</h2>
        <ul>
          <li>区分文档信息与正文内容。</li>
          <li>用标题和列表表达信息层次。</li>
          <li>检查样式与脚本的资源路径。</li>
        </ul>
      </section>
      <section id="notes" aria-labelledby="notes-title">
        <h2 id="notes-title">实践记录</h2>
        <article>
          <h3>第一次结构检查</h3>
          <p>记录日期：<time datetime="2026-01-15">2026 年 1 月 15 日</time></p>
          <p>浏览器显示内容之后，还需要核对实际的 DOM 结构。</p>
        </article>
      </section>
      <p id="resource-status" role="status">脚本尚未执行。</p>
    </main>
    <footer>
      <p><small>示例页面，不收集访问数据。</small></p>
    </footer>
  </body>
</html>
```

导航使用链接，因为操作目的是移动到另一个位置；如果操作目的是提交或切换状态，则通常应使用按钮。`time` 的机器可读日期与中文展示文本各司其职。示例给两个分区提供明确标题，并用 `aria-labelledby` 引用标题，而不是重复维护一份隐藏名称。

现在只有入口文件时，正文仍然能阅读，但样式和脚本请求会失败。下一步补齐资源，观察渐进增强：基本内容不依赖脚本生成，脚本加载失败时读者仍能访问笔记。这种结构比先放空容器、再等待脚本拼出所有正文更适合简单的内容页面。

## 第二步：补齐样式与脚本资源

在同一目录新建 `styles.css`。规则限制正文阅读宽度，保留链接下划线，并用可见轮廓标明键盘焦点。全局盒模型让宽度计算更直观；这里不使用重置所有默认样式的大型方案，以便你看到浏览器原有的语义排版。

```css
* {
  box-sizing: border-box;
}
body {
  margin: 0;
  color: #172033;
  background: #f4f6fa;
  font: 1rem/1.75 system-ui, sans-serif;
}
header, main, footer {
  width: min(100% - 2rem, 48rem);
  margin-inline: auto;
}
nav {
  display: flex;
  flex-wrap: wrap;
  gap: 1rem;
}
section {
  margin-block: 2rem;
}
a {
  color: #174ea6;
  text-underline-offset: 0.2em;
}
a:focus-visible {
  outline: 3px solid #174ea6;
  outline-offset: 4px;
}
```

再新建 `main.js`，内容如下。脚本只增强状态提示，不负责生成主要内容。`defer` 使外部经典脚本在文档解析完成后执行，避免查询节点时正文尚未建立；多个此类脚本通常按文档中的顺序执行。它与让脚本尽快执行的 `async` 不同，后者不保证这种依赖顺序。

```javascript

if (status) {
  status.textContent = "脚本已执行，页面资源路径正确。";
}
```

刷新入口文件，预期看到浅色背景、有限宽度正文以及“脚本已执行”的文字。注意，这是你运行时应检查的结果，不是本文已经替你执行的记录。通过禁用 JavaScript 再刷新，可以验证主体内容是否仍然存在；样式禁用后，也应保留合理的阅读顺序。

## 资源路径、加载时机与内容责任

相对路径从当前文档 URL 出发解析，`./styles.css` 指向文档同级文件；以斜杠开头的路径从站点根目录出发，在子路径部署时含义可能不同。浏览器不是从你编辑器的工作目录寻找资源。因此，排查资源错误时应查看网络面板里的最终请求地址，而不是只检查文件名看起来是否相似。

样式表通常影响首次绘制，因为浏览器需要知道元素如何展示。脚本的加载和执行也可能占用主线程。对于这个小页面，明确加载顺序比提前引入复杂性能配置更重要。不要随意给所有资源加预加载：预加载会参与网络竞争，只有确认关键资源确实需要更早获取时才有价值。

图片属于内容时，应写清其替代文本与固有尺寸；纯装饰图片的替代文本可以为空。替代文本描述图片在当前上下文中传达的信息，而不是机械重复“这是一张图片”。宽高有助于浏览器在下载完成前预留空间，减少布局移动。对首屏关键图片不要不加区分地懒加载，非首屏图片则可以按实际需求考虑。

本篇没有引入外部图片，因此练习不会依赖某个远程图片服务是否可用。实际项目中还需要确认资源授权、缓存策略和隐私边界，这些问题不能仅凭 HTML 属性解决。文档负责声明资源，服务端和发布环境负责正确交付资源。

## 检查结果与错误排查

先检查标签页标题和中文显示，再检查导航是否滚动到对应分区。打开元素面板确认主体在 `main` 中，两个主题分区的标题层级一致，所有 `id` 都唯一。按 Tab 应依次访问两个导航链接，焦点轮廓不应消失。把窗口缩小后，导航应允许换行，正文不应依赖固定桌面宽度。

若页面中文乱码，检查文件实际保存编码，而不是只增加字符集声明；声明不能把已经保存错误的字节自动修复。若样式没有出现，检查大小写、文件扩展名和最终资源地址。某些系统会把文件保存成额外带 `.txt` 的名称，编辑器显示的短名称可能掩盖这一点。

若状态文字没有改变，检查控制台错误、脚本路径与 `defer` 是否存在。若点击锚点没有定位，检查链接中的片段是否与目标 `id` 完全一致。若 DOM 与源代码不一致，优先检查不合法嵌套，例如将块级段落放进另一段落；浏览器的解析修复不是可以长期依赖的业务逻辑。

## 标准模式与结构验收

文档开头的类型声明帮助浏览器进入标准模式，而不是沿用历史兼容布局。它不是内容标签，也不是选择某个发布年份的开关。遗漏声明时，某些尺寸和排版规则可能进入怪异模式，使后续 CSS 调试建立在错误前提上。完成入口文件后，应同时检查声明、语言与标题，而不只检查正文是否出现。

## 练习与官方参考

把“实践记录”扩展为两篇独立笔记，每篇有自己的三级标题、机器可读日期和两段正文。新增一个“常见问题”二级分区，并在导航中加入其锚点。验收时关掉样式与脚本，确认阅读顺序仍然清楚，再恢复资源确认增强效果。不要用连续空格或多个换行承担布局职责。

进一步思考：如果页面没有独立成篇的内容，`article` 是否仍然合适？如果新增按钮只负责跳到页面底部，应选择链接还是按钮？给出操作目的和内容关系，比背诵元素清单更能检验理解。完成后可继续阅读 [原生表单与约束验证](./forms.html)。
