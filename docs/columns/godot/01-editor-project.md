# 第 01 章：编辑器、稳定版本与第一个项目

游戏引擎不是一套画图软件，也不是一个替你完成玩法的脚手架。它把资源加载、场景组织、输入、物理、渲染与音频放在同一个运行循环里。第一章的目标是独立建立一个可以启动、暂停观察、修改后再启动的项目，并能解释编辑器中看到的节点与正在运行的节点为什么可能不同。先建立这条反馈路径，后面的代码才有可验证的落点。

## 1.1 选对版本和发行形态

本专题以 **2026-10-23 核验的 Godot 4.7.2 stable** 为教学目标，具体发布证据见[专题首页](./index.md)。下载页的标准版使用 GDScript；.NET 版为 C# 提供相应支持，但不是“更完整的标准版”。对于本教程，标准版已经足够，不需要安装 .NET SDK。导出模板是生成目标平台程序需要的运行组件，也不是另一个编辑器。

版本判断要同时看版本号、发布阶段、发布日期与官方下载入口。beta、RC、dev 和 nightly 即使数字更大，也不应替代稳定版本作为第一次项目的默认选择。官方文档的 `stable` 别名会变化，因此章节固定引用 `/en/4.7/`。碰到不认识的属性，先在相同版本类参考里检查，不要把搜索结果中 Godot 3 的节点名直接搬进来。

示例已在官方标准版 `4.7.2.stable.official.ed1daf0bf` 通过导入、规则冒烟与场景启动验证，也在 4.6.2 基线运行。源码使用共同的 Godot 4 API；引擎启动通过并不证明所有平台已经可交付。读者安装目标版本后，应重新执行第十五章的导入与冒烟命令。教学目标、文档基线和运行证据是三件事，工程记录需要分别写清楚。

## 1.2 项目是资源根目录，不是某个场景

`project.godot` 确定项目根目录、主场景、输入动作与渲染设置。`res://` 指向这份配置所在的目录，而不是操作系统当前目录；`user://` 指向应用可写的用户数据位置。发布后的资源可能打包到只读文件中，所以存档不能写回 `res://`。先认识这两个路径，就能避免“编辑器能保存，导出后失败”的常见问题。

`scenes/`、`scripts/` 等名称只是本教程的组织约定，并不是引擎强制目录。小项目按资源种类分组便于学习；大项目也可以把一个功能的场景、脚本与资源放在一起。真正重要的是路径稳定、责任清楚、能够从干净目录重建，而不是提前建立几十个空目录。`.godot/` 是导入与编辑器缓存，不是手工编写的源代码。

完整示例位于仓库 `examples/godot/`。它没有外部图片，也无需依赖安装。目录最小骨架如下：

```text
project.godot
scenes/main.tscn
scenes/player.tscn
scripts/main.gd
scripts/player.gd
```

## 1.3 用编辑器建立一份独立实验

1. 在项目管理器选择新建，指定一个空目录，渲染器选择 Compatibility。本项目优先覆盖普通桌面设备与后续 Web 实验，不需要先启用高成本 3D 特效。
2. 新建 2D 场景，根节点命名为 `Main`，保存为 `scenes/main.tscn`。添加 `Polygon2D`，在多边形编辑工具中画出三角形并设置明亮颜色。
3. 给根节点附加 `scripts/main.gd`，保留 `extends Node2D`。在项目设置里把视口宽高设为 960×640，设置深色背景。
4. 按 F6 运行当前场景；再按 F5 运行项目，在提示中把当前场景设为主场景。关闭运行窗口后，再次 F5 确认无需重新选择。
5. 把项目关闭再重新导入。只有重新打开仍能运行，才证明配置已经保存，而不是靠编辑器当前状态碰巧工作。

场景树显示结构，检查器显示所选对象的属性，文件系统面板显示项目资源，底部输出与调试器显示运行信息。二维视图只是其中一块工作区域。节点创建、属性设置、脚本附加和资源保存应各自确认，不能用“画面上有一个三角形”替代这些检查。

下面的片段可以挂在上述 `Main` 上，用于观察生命周期。它是独立实验，不是毕业项目 `main.gd` 的替换内容。

```gdscript
extends Node2D

var elapsed: float = 0.0

func _ready() -> void:
	print("Main ready: ", get_path())

func _process(delta: float) -> void:
	elapsed += delta
	if elapsed >= 1.0:
		set_process(false)
		print("One second observed")
```

`_ready()` 表示节点及其子节点完成相关入树准备，不是“所有资源永远都准备好了”。`_process()` 每个渲染帧调用，`delta` 是相邻调用的时间间隔。这里累积时间而不是计算帧数，因此在不同帧率下都大约一秒输出第二条信息。稍后会把物理更新放到另外的回调中。

## 1.4 本地场景树与远程场景树

运行项目后，场景面板可切换 Local 与 Remote。Local 是编辑器打开的场景定义；Remote 是实际运行进程中的节点实例。毕业项目的墙体、晶体与 HUD 子节点由脚本创建，因此它们可能不出现在 Local 中，却能在 Remote 找到。没有区分两者时，开发者容易误判“节点没创建”或把临时运行修改当成已经保存。

在 Remote 选择玩家，观察 `position` 是否随着移动改变；选择 HUD，观察标签文本如何随收集变化。临时修改运行属性可帮助定位问题，但通常不会自动写回源场景。要保留改动，应在停止运行后更新本地场景或脚本。调试器中的断点同样只停住执行现场，不会替你修复资源配置。

完整项目可以从仓库根目录运行：

```bash
godot --version
godot --path examples/godot
```

如果系统没有 `godot` 命令，使用引擎可执行文件的完整路径。macOS 应用包目录不是可执行文件本身；不要因为终端找不到命令就重新安装项目依赖。先在项目管理器确认编辑器能运行，再处理命令行路径，这样可以把工具发现问题与游戏问题分开。

## 1.5 保存、导入和运行的关系

保存场景会写入节点及资源引用；保存脚本会更新源码；导入则把原始资源转换成引擎使用的格式。第一次打开项目可能需要等待导入完成。修改源图片后也会重新导入，但不代表已经把场景实例中的属性改好。操作之间存在明确边界，排错时应该确认故障发生在哪一步。

不要手工修改 `.godot/` 里的转换结果，也不要把编辑器缓存当作必须分发的素材。可以保留场景、脚本、原始资源与引擎生成的引用元数据，并让目标机器重新导入。后续第十二章会解释 UID 和导入设置的区别。现在先做到关闭编辑器后重新打开仍然有相同效果。

## 1.6 正常与异常验证

正常路径：F5 能启动预期主场景，Remote 中有 `Main`，输出只出现一次准备消息与一次时间消息，关闭窗口后编辑器没有残留错误。完整示例还应出现五枚金色晶体、两名红色守卫和顶部按钮。画面内容与源目录中的 README 应一致。

异常路径：在独立实验中临时把主场景设置为空，确认 F5 提示缺少入口而不是偷偷运行别的场景；恢复设置后重启。再把脚本中的节点路径写错，观察调试器指出具体行号。练习结束要恢复源文件，不能通过隐藏错误输出宣布通过。

| 现象 | 先检查 | 原因与处理 |
| --- | --- | --- |
| F6 正常，F5 运行旧画面 | 主场景配置 | 当前场景与项目入口不同 |
| 有节点但画面空白 | 可见性、位置、相机 | 结构存在不等于在视口内 |
| 重启后修改消失 | 场景和资源保存状态 | Remote 改动不等于源文件改动 |
| 命令找不到 | 可执行文件路径 | 与 GDScript 或导入缓存无关 |
| 属性名称不一致 | 引擎和文档版本 | 先查 Godot 4.7 类参考 |

## 1.7 作业与验收

独立建立一个包含根节点、图元和计时脚本的小项目，关闭后重新导入并运行。提交项目目录结构、实际引擎版本和两条运行输出；解释 F5 与 F6 的差别，指出运行时新增节点应在哪里观察。不要只提交截图，因为截图不能证明项目可以重建。

验收标准是入口明确、没有脚本错误、重新打开后行为一致，且能说明 `res://` 与 `user://` 的用途。进阶练习是改变窗口尺寸并记录图形和 UI 的变化，只记录现象，暂时不要通过任意缩放掩盖布局问题。下一章开始把这些运行节点背后的规则写成可检查的静态类型代码。
