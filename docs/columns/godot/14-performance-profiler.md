# 第 14 章：帧预算、Profiler 与有证据的优化

“帧率不高”只是现象，可能来自脚本、物理、渲染、资源上传或等待。本章建立测量、定位、单变量修改与回归的流程。毕业项目规模很小，没有给出经过真机验证的性能目标；它适合作为基线练习，不适合用空场景的高帧率证明大型游戏架构正确。

## 14.1 先定义预算

六十帧每秒对应约十六点六七毫秒一帧，一百二十帧对应约八点三三毫秒。预算不仅包含脚本，还包括引擎、物理、渲染提交与 GPU 工作。平均帧率掩盖短暂卡顿，至少同时记录典型帧、较高分位帧时间和最大尖峰，特别关注生成关卡、首次效果与存读档。

先确定目标设备、分辨率、渲染器、电源状态与玩法规模。桌面插电与手机热降频不能混成一组结果，编辑器调试版与导出发布版也不可直接比较。无垂直同步时的一千帧空场景，不回答玩家设备能否稳定运行复杂关卡。

建立固定路线与场景，例如同样五枚晶体、同样两名守卫、固定移动路径和二十次重开。记录引擎版本、构建模式与窗口尺寸，区分冷启动和暖缓存。测量时避免后台大任务和持续日志；条件无法控制时注明不确定性，而不是用单次数字排序方案。

## 14.2 编辑器分析步骤

打开项目，在底部 Debugger 的 Profiler 中启动采集，然后运行主场景。先保持静止，再移动、收集、存档、加载和重开，让不同动作在时间线上可以对应。停止采集后选择异常帧，查看脚本函数耗时与调用次数，而不是只看整个运行的累计最大函数。

同时查看 Monitors 的节点、对象、内存、绘制调用与物理相关计数。需要图形分析时使用 Visual Profiler 或适合目标图形接口的外部工具，并核对该渲染器的支持范围。脚本 Profiler 不等于 GPU 分析器，GPU 忙碌也可能在 CPU 侧表现为等待。

先问尖峰发生在哪个动作，再看对应线程和子系统。首次显示新材质可能触发 shader 编译，首次资源加载可能发生读取与上传，重开可能分配大量节点。把所有问题都归因于 GDScript 太慢，会把优化带到错误方向。

## 14.3 最小运行监视器

下面完整脚本挂在独立调试 Node 上，每秒打印一次引擎监视值。它不写用户数据，不改变游戏规则，不是精确 GPU 帧时间分析：

```gdscript
extends Node

var remaining: float = 1.0

func _process(delta: float) -> void:
	remaining -= delta
	if remaining > 0.0:
		return
	remaining = 1.0
	var process_ms: float = Performance.get_monitor(
		Performance.TIME_PROCESS
	) * 1000.0
	var nodes: int = int(Performance.get_monitor(
		Performance.OBJECT_NODE_COUNT
	))
	var memory_mib: float = Performance.get_monitor(
		Performance.MEMORY_STATIC
	) / (1024.0 * 1024.0)
	print("process_ms=%.3f nodes=%d memory_mib=%.2f" % [
		process_ms, nodes, memory_mib
	])
```

TIME_PROCESS 是引擎暴露的处理时间监视项，不应把它直接解释为某个函数、完整 GPU 帧或端到端输入延迟。监视项支持情况与构建有关，零值不总意味着完全没有开销。为了复现实验，先记录未加探针的基线，再评估采样与输出本身是否影响结果。

更精细的局部操作可用 Time.get_ticks_usec 前后取差，测量同步函数耗时；它不能跨越异步任务就假定只测到了目标函数。资源读取、线程等待与渲染上传要单独分阶段计时，并避免测量代码改变原来的执行顺序。

## 14.4 CPU 和物理瓶颈

脚本瓶颈常见于每帧重复查找节点、构造大字典、拼接字符串、重复刷新未变化的 UI 和高频搜索。优化先考虑减少不必要工作，再考虑微小语法差异。使用 @onready 缓存固定节点引用合理，但动态节点被重建后必须更新引用，缓存不是无条件正确。

本项目 HUD 每帧更新计时与状态文本，是小规模、可理解的实现。若测量证明文本格式化造成开销，可以把数字刷新频率与规则更新分开，只有显示值变化才写入 Label。不能因为看见每帧赋值就擅自认定必须重构；较小实现的维护成本也是预算。

物理开销与活动体、碰撞形状、查询数量和接触复杂度有关。把无关层从 mask 排除，使用合适简单形状，错开大量感知查询，比任意降低物理频率更可控。降低物理频率可能改变碰撞与控制体验，必须重新验证穿透、跳跃和区域触发。

导航、AI 和动画也可以采用不同决策频率，但角色移动应遵循物理步长。暂停和远距离休眠需要完整唤醒规则；一个被停止更新的敌人可能仍留有碰撞或未清除目标。省掉更新不能让玩法出现不可解释的不一致。

## 14.5 GPU 与绘制成本

GPU 压力可能来自像素数量、材质复杂度、透明过绘、阴影和后处理，不只是多边形数量。把分辨率暂时降低，如果耗时明显改善，说明像素相关成本值得调查，但仍需要分析具体效果。只降低角色模型面数，可能完全没有触及全屏特效瓶颈。

二维大量透明粒子和叠层 UI 会反复绘制相同像素；三维透明面、实时阴影与重叠灯光也可能昂贵。关注绘制调用、材质切换、可见范围与遮挡策略，再考虑图集、MultiMesh、LOD 等工具。MultiMesh 适合大量相似实例，却会改变逐实例管理与可见性粒度，不能无条件替代所有节点。

首次 shader 或资源准备导致的尖峰，应单独测量冷启动。预热会把成本移动到加载阶段，并不会让成本消失；预热范围太大还会增加启动时间与内存。需要确定玩家可接受的加载边界，然后验证进入实际关卡后是否仍出现未覆盖的编译。

## 14.6 内存与生命周期

Node 的 queue_free 在延迟阶段释放，并非调用后立刻消失；RefCounted 在引用归零后释放，循环引用或长期集合可能让资源保留。资源加载有缓存与共享，同一图片被多节点使用并不一定意味着重复占用完整纹理；动态生成的大图片却可能确实创建了多份数据。

本项目重建关卡时先 remove_child，再 queue_free，避免旧节点在树中继续参与下一局。测量重复重开需要等延迟释放完成，再比较节点与资源数量。新旧关卡交替瞬间的峰值不等于泄漏，二十次之后持续上升才值得调查。

不要把每次资源加载后的内存上升都称为泄漏，缓存、音频解码和纹理上传都可能形成正常高水位。区分稳定峰值、持续增长和可释放资源，并找到保留引用。对象池也会刻意留住对象，降低分配成本但提高常驻内存，它是一项权衡而不是免费优化。

## 14.7 线程不是第一反应

Godot 提供 Thread、WorkerThreadPool 和服务器相关能力，但场景树与许多资源访问不是随意线程安全的。适合后台的工作应尽量处理独立数据，结果再通过安全边界提交到主线程；不能把 `_physics_process` 整段搬到工作线程并继续操作角色节点。

共享字典、资源修改与任务取消都需要明确所有权。线程加锁可能产生竞争和等待，小任务调度开销甚至超过计算收益。先证明某项纯数据工作足够重，再设计线程版本，并验证退出场景、重新启动与错误取消。加载线程接口与手工开线程也不是同一工作流。

## 14.8 优化验证与作业

每次只改一项，使用同一场景与路线重复采样。优化报告应包含修改前后条件、帧时间分布、调用次数、内存峰值，以及规则回归结果。指标改善但输入延迟、碰撞或画质退化，不算无条件成功；需要说明取舍并得到目标体验的认可。

异常验证加入大量实例、低帧率、连续重开、快速读档、窗口切换和冷启动。怀疑性能导致错误时先降低场景到最小复现，区分时间单位错误与负载问题。不能删除碰撞、关闭效果后只报告更高帧率而不披露行为变化。

作业是在独立实验中把守卫数量提升到可测量规模，定位一项真实瓶颈并做单一优化。验收要求保留前后证据、同样输入路线、说明预算与设备、规则验证通过，以及解释为什么没有采用另一种成本更高的方案。没有目标设备数据时，只提交实验结论，不宣称达到发布性能。
