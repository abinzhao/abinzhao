# 第十章：用行为测试守住 Harness 契约

一个 Agent 演示能回答问题，不代表它的工程边界正确。网络包换一种切分方式，中文可能损坏；工具参数多一个字段，可能突破原定能力；运行中断后，下一次请求可能读到半轮历史。模型回答的不确定性还会掩盖这些缺陷：今天“看起来正常”的结果，明天未必能复现。

本章只解决**如何验证 Harness 自身的行为契约**。把协议、工具边界、状态转换与真实模型效果拆开，用 Node.js 自带测试能力构造确定输入，再断言可观察结果。无需引入第三方测试运行依赖，也不需要用一台真实模型服务器证明每一个控制流分支。

参考资料固定为 **2026-10-17** 核验的 DeepSeek Harness `0.2.1-alpha.5`、提交 `1517a4dbca0a2789ff1d41ba439600f8547d23fa`。上游是 TypeScript 与 Cordis 插件框架，测试布局和契约比本例复杂；这里使用独立 Node.js 22 原生 ESM 项目的 `node:test`，不是上游测试套件的移植。

## 一、确定性测试与模型效果有不同判据

确定性测试要回答“给定这些输入，程序是否采取了约定行为”。例如收到截断流必须拒绝结算，工具结果必须与调用 ID 配对，取消运行不得进入完成历史。这些规则可以用精确断言验证，不需要让模型随机选择工具后再猜测哪种结果算正确。

模型效果评测则要回答“在真实问题上，模型是否正确选择证据并给出有用回答”。它依赖真实模型、上下文、任务集和评价标准。provider 替身返回固定字符串，只能驱动 runner 的状态机，不能证明模型会生成同样回答，更不能证明引用准确率。

即使真实 provider 请求使用 `temperature: 0`，也不等于整个模型系统具有完全确定性。模型版本、服务实现和执行环境都可能影响结果。因此工程回归测试不应依赖“这次模型恰好说对了”，模型验收也不应拿一个替身的 `verified answer` 冒充真实输出。

## 二、先写失败行为，再实现最小规则

从零开发时，先写一个明确失败的行为用例：输入是什么，期待的拒绝或输出是什么，以及缺少实现时怎样失败。运行它确认失败是因为行为尚未实现，再补最小代码，最后运行相关回归。这比写完所有模块后才添加一组只覆盖正常回答的测试更容易发现契约漏洞。

当前入口测试会动态导入 `src/index.mjs`，导入失败时得到空对象，然后断言 `runAgent` 必须是函数。这个设计能在尚未实现入口时形成清晰失败；但异常导入也可能来自语法错误，所以看到“未实现”提示时仍要检查直接导入的实际错误，不能只依据断言文案定位根因。

```js
const api = await import('../src/index.mjs').catch(() => ({}));

test('the tutorial exports a real runnable harness', () => {
  assert.equal(typeof api.runAgent, 'function', 'runAgent has not been implemented');
});
```

对流式 provider，先规定“有文字但没有完成标记，不得返回已结算回复”。若实现仅拼接文字然后返回，用例会失败；加入完成标记检查后才能转绿。不要为了通过而把断言改成“返回任意字符串”，那是在撤销问题，而不是修复实现。

这是一种开发方法，不是对当前全部代码历史的声明。仅凭已经通过的测试文件，不能证明每项功能都经历过实际红灯阶段。本章展示如何构造失败证据和理解现有回归，不把未核验的开发过程写成既成事实。

## 三、协议测试要改变包边界

网络传输的 chunk 不等于 SSE 事件。当前测试把含中文、CRLF、注释和完成标记的字节序列逐字节送入 `ReadableStream`，强迫 UTF-8 字符跨 chunk。断言解码结果仍然是完整 JSON 和 `[DONE]`，而不是乱码或多余注释。

这个用例验证 `TextDecoder` 的流式解码与 SSE 行处理；测试名还提到工具增量，但具体工具参数组装发生在另一个 HTTP provider 用例中。阅读测试时要看实际输入和断言，不能只把测试标题当成覆盖范围清单。

HTTP fixture 使用真正的 `node:http` 服务，监听 loopback 的随机端口。它读取真实请求体，依次发送文字、工具调用前半段参数和后半段参数，最后发出完成标记。provider 通过真实 fetch 接收响应，断言参数拼成 `{"path":"guide.md"}`，并检查请求里的模型名和 `stream: true`。

这里的“真实”是指 HTTP 套接字、请求编码和流读取真实发生，不是服务背后运行了语言模型。返回内容由测试预设，因此协议结果可复现。对网络边界使用真实 fixture，对模型决定使用替身，正是避免把传输错误和模型质量混在一起的办法。

## 四、工具测试需要真实文件边界

工具测试创建临时工作区和另一个外部目录，写入可读文件、超大文件和指向外部文件的符号链接。它不是仅替换文件系统函数返回“拒绝”，而是让实际 `realpath`、打开文件和有界读取经过真实文件系统。

断言覆盖正常读取、目录穿越、静态符号链接逃逸、未知参数字段、文件超限和不存在的工具。`assert.rejects()` 用于异步拒绝，`assert.throws()` 用于同步异常，选错形式可能没有真正等待目标失败，反而使测试失去意义。

这一组测试证明常见路径和大小约束，不证明工具具有操作系统级沙箱。攻击者并发替换祖先目录属于 README 明确排除的威胁模型，当前测试没有覆盖。安全结论要与实际防护和测试证据同范围，不能因为几个逃逸案例被挡住就宣称任意攻击都不可行。

临时文件内容是合成证据，不能用真实凭据或个人文件当 fixture。测试需要模拟私密边界，但不需要接触真实敏感数据。临时目录创建和测试资源释放也应纳入维护责任，避免测试失败后遗留长期占用或污染工作区。

## 五、状态测试要观察下一次回放

只断言当前函数抛错不够。一个非法 session 事件可能先写进磁盘，再在内存更新时抛错；这次调用看起来“拒绝了”，下一次打开却发现文件已经损坏。因此状态测试必须核对拒绝之后的可持续使用能力，而不是仅检查异常存在。

现有回归先写 begin，再尝试把未结算运行结束为 completed，断言拒绝；随后写合法 failed 结束，重新打开 session，确认历史为空。当前源码在磁盘追加之前调用 `checkTransition()`，对应的正是“非法状态不得污染耐久日志”这条行为规则。

失败与取消回放测试还验证 completed 运行保留、cancelled 运行排除、损坏 JSON 拒绝、非法 session ID 拒绝。runner 步数上限用永远返回工具调用的替身触发，断言达到限制后历史为空。这些断言观察的是运行后果，不依赖内部变量叫哪个名字。

工具循环测试则用两次确定返回驱动真实 runner：第一步调用读取工具，第二步必须看见文件证据，再返回最终回复。断言消息角色为 user、assistant、tool、assistant，并检查结束事件和磁盘没有逐字增量。这样一次用例穿过工具、会话、循环三条真实边界。

## 六、并发测试不要依赖猜测时长

Web 并发测试通过 Promise 通知第一个运行已经开始，再发送第二个请求，断言返回 409。随后取消第一个连接，等待运行 signal 的 abort 被观察到。它没有使用“睡一秒应该够了”来猜第一个请求是否已经取得锁。

这种同步方式把时序条件写进测试契约：先接纳第一个，后拒绝第二个，最后观察取消。随机端口避免固定端口冲突，`finally` 关闭服务器，减少测试间资源干扰。测试结束不只是断言结束，还应确保没有仍在运行的服务器阻止进程退出。

另一条 Web 测试读取实际 HTML，检查其中包含控制器代码，发送真实同源请求验证 SSE，再验证跨 Origin 请求被拒绝和错误内容类型得到 415。不过读取 HTML 的字符串不是 DOM 执行，测试并没有在浏览器里点击按钮，也没有证明脚本文字一定不会被渲染器执行。

同样，慢消费者中止、错误 Host、请求超限、九十秒超时都可以从当前源码确认，但没有对应逐项自动断言。记录这些缺口是为了扩展时有明确回归目标，不是把源码存在某个 `if` 当成行为已经全面实测。

## 七、按当前目录约定运行

下载[完整源码](/downloads/agent-harness.zip)，进入 example 根目录后，运行全部行为测试：

```sh
node --version
npm test
node src/cli.mjs --help
```

这组命令不需要 Ollama，也不安装第三方依赖。核心文件有十二项测试，Web 有三项，CLI 与工作区初始化有两项，合计十七项。直接运行 CLI 帮助应退出为零，并展示 MODEL 和 `--web`。它们分别验证行为与入口，不应把帮助文本出现模型名理解成已经连接模型。

子进程入口必须相对于测试文件定位，不能假设调用者总在网站仓库根目录。CLI 用例通过 `new URL('../src/cli.mjs', import.meta.url)` 找到入口，再用 `fileURLToPath()` 转成系统路径。这与模型或工作区配置无关：测试自身先建立稳定的文件关系，才有资格判断入口的行为。

## 八、怎样补充下一条有效测试

先从一个尚未验证的完成标准出发，例如“等待重试时取消，不得产生第二个 HTTP 请求”。注入可计数的 fetch，安排第一次收到 503 后触发取消，再断言 complete 拒绝且请求计数不增长。只断言最终报错不够，因为错误前可能已经额外请求过一次。

再例如“当前轮工具结果超预算，下一步不得调用 provider”。先用替身生成一个超过剩余预算的工具结果，记录 provider 调用次数，再断言运行失败、没有新的完成历史。这比仅断言某个工具返回值很大，更贴近请求预算的真实行为。

测试数据应与目标相关。不要用永远成功的 session 替身来验证真实持久化，不要用直接返回 assembled reply 的 provider 来证明 SSE 解析，也不要让无意义 Mock 把被测边界完全替换掉。替身可以隔离另一层，但必须把要验证的这一层留在真实路径上。

修改实现后先运行最小相关用例，再运行核心与 Web 集合，最后在适当工作目录运行全部测试。若失败来自端口、路径或 Node 版本，应提供证据区分测试环境与行为回归；若来自真实断言，则修复实现，不放宽完成标准。

## 九、真实模型是另一份验收

本机安装 Ollama 和支持 tools 的模型后，可以在 example 根目录运行：

```sh
ollama list
MODEL=qwen3:4b npm start -- "阅读 guide.md，说明没有哪些工具，并引用文件路径"
```

人工检查它是否实际读取证据、是否正确指出没有 Shell 或写文件工具、是否引用真实路径、是否解释缺失信息。重复任务、记录模型版本和失败案例，才有讨论效果质量的基础。当前核验环境没有 Ollama 服务，十七项确定性测试通过不代表这份模型验收完成。

本章的完成标准不是“测试越多越好”，而是关键边界拥有能失败的断言，协议与状态可复现，测试目录和资源责任明确，真实模型效果单独报告。这才让 Harness 的工程正确性能够独立于一次漂亮演示成立。
