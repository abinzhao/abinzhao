# 岗位职责与能力地图：对任务结果负责

## 学习目标

本章解决三个问题：产品经理究竟对什么负责，必须理解技术到什么程度，以及如何证明自己具备能力。学完应能写出一份可评审的结果责任书，解释模型质量、任务质量与业务结果的区别，并在权限、安全和上线决策中找到明确负责人。

“Agent 产品经理”并没有本课程可验证的统一行业职级标准。不同公司可能由平台产品、应用产品、业务负责人或技术负责人承担相关工作。[GitLab 的公开岗位手册](https://handbook.gitlab.com/job-families/product/product-manager/)提供了一种结果与跨职能协作实践，但不能推导所有企业都采用相同分工。以下能力地图是教学框架，不是招聘认证。

## 一、先确定责任对象

传统功能可以描述为“点击后按规则完成操作”。Agent 功能则需要进一步回答：目标由谁设定，行动如何选择，什么时候必须暂停，哪些业务状态代表完成。用户看到一句“已处理”，不意味着后台真的处理成功；模型返回正确格式，也不意味着请求获得授权。这两个差距分别指向结果判定和执行控制。

产品经理负责定义可接受的任务结果，而不是替工程团队承诺每次模型输出一致。以“澄明服务台”为例，结果不是“生成三百字答复”，而是“专员取得来自已授权有效手册的答复草稿，能检查证据，在证据不足时被明确告知缺口”。任务需要改工单时，草稿与写入是不同结果，必须分别验收。

责任可分成三层。第一层是用户价值：问题值得解决吗，用户是否愿意改变工作方式。第二层是任务契约：允许的输入、证据、动作、停止条件和接管路径是什么。第三层是经营与治理：质量不足、成本超限或发生泄露时，谁决定暂停、回滚和扩量。不能因为模型由第三方提供，就把后两层责任转交给厂商。

## 二、理解技术不等于接管技术岗位

产品经理需要读懂系统的因果关系。例如检索遗漏会影响证据覆盖，证据过期会影响答案有效性，授权校验缺失会影响数据边界，重试策略会影响重复写入。只有理解这些关系，才能讨论合理的需求、优先级和验收；但不必为了入门先掌握预训练算法。

[OpenAI 工具调用文档](https://platform.openai.com/docs/guides/function-calling)描述的是模型提出调用、应用执行、再回传结果的流程。它说明产品控制必须落实到应用，而不是停在提示词里。[Anthropic 的 Agent 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)进一步区分轨迹与实际结果，提示不能只评审聊天文本。这两种证据共同支持“围绕任务和状态管理产品”的方法。

| 能力领域 | 必须能解释的机制 | 可检查的能力证据 |
| --- | --- | --- |
| 用户与业务 | 高频不等于高价值，替代方案会改变收益 | 有反例的任务研究与基线说明 |
| 系统与控制 | 模型建议、应用校验、实际执行相互分离 | 输入到业务状态的流程走查 |
| 规格与体验 | 不确定性需要澄清、暂停、拒绝与恢复 | 状态表和带失败路径的 PRD |
| 数据与评测 | 指标依赖分母，评分器也会出错 | 可复算指标和校准记录 |
| 商业与资源 | 总成本包括复核、失败、运行与支持 | 敏感性测算及预算停止条件 |
| 安全与治理 | 用户同意不自动等于全部合法授权 | 数据流、威胁模型和责任表 |

初学者可以先完成一条只读任务的闭环；更熟练者能够处理跨系统动作与未知结果；负责人还要管理多团队依赖和经营风险。这里的层次用于安排练习，不代表“初级、中级、高级岗位”的行业门槛，也不以会多少工具作为升级标准。

## 三、交付样例：结果责任书

以下全部为教学假设，研究、评测和上线均未执行。可替换组织和任务字段，但不能把假设改写为事实。

| 字段 | 已填写样例 |
| --- | --- |
| 产品对象 | `tenant-lab` 内部服务台专员，处理已授权知识查询 |
| 待验证问题 | 专员寻找有效规则和核对适用条件的工作存在可减少的负担 |
| 首版价值 | 辅助查找、形成草稿、显示证据与缺口；不承诺自动结案 |
| 成功判定 | 按任务标准判定证据、适用条件和草稿可用性；由独立复核者评分 |
| 禁止范围 | 退款、外发消息、账户权限、人事决定、跨租户检索 |
| 产品责任 | 确定任务边界、验收指标、扩量条件和暂停建议 |
| 工程责任 | 身份授权、检索执行、日志、幂等、故障与部署实现 |
| 知识责任 | 业务负责人批准政策、适用范围、版本与失效日期 |
| 安全责任 | 安全人员复核威胁控制；法务判断实际业务法规适用性 |
| 最终上线权 | 教学案例指定业务负责人批准；其他角色可按约定阻断 |
| 证据状态 | 文档走查待执行；真实用户数据、模型结果和生产证据均缺失 |

这份责任书的重要部分不是职位名称，而是“谁可阻断”。如果安全负责人认为跨租户测试未通过，产品负责人不能用体验指标覆盖这个问题。如果知识负责人没有批准政策版本，工程团队也不能凭页面可访问就把内容作为业务真相。

## 四、把责任落实到评审与决策

责任表只有与决策记录关联，才不会成为装饰。教学案例采用以下节奏：发现评审确认问题和研究授权；规格评审确认知识、工具、交互与控制边界；上线评审确认评测证据、预算、事故值守与回滚；运行评审分析真实任务失败。会议频率由风险和团队规模决定，不设“所有团队每周必须开几次会”。

每项争议建立短决策记录，保留“问题、证据、备选方案、选择、代价、重审条件”。例如，工程建议首版开放工单状态写入，产品选择先只读，理由不是“Agent 不成熟”，而是尚无审批绑定、幂等与未知结果恢复的验证记录。重审条件是这些契约和测试补齐，而不是过一个月自动放开。

产品经理还应区分决策类型。可逆的文案调整可以低成本试验；连接真实工单、改变保留策略或扩展权限，涉及更大的外部影响，需要相应批准和证据。把所有问题都交给负责人审批会造成瓶颈，把所有问题都当成可逆实验则会损害安全。

## 五、失败案例与纠偏

**失败一：把演示效果当岗位能力。** 演示只覆盖一条顺利路径，没有来源过期、授权失败或取消场景。问题不在于演示本身，而在于从演示推导上线能力。纠偏是为同一任务补充状态与失败证据，说明哪些结论仍未测。

**失败二：产品承担所有角色。** 产品经理自行写政策、批准风险并给自己的答案评分，形成自证循环。小团队可以一人兼任多个角色，但应明确角色冲突，关键结果引入独立复核；没有复核条件时限制能力和暴露范围，不用头衔掩盖缺口。

**失败三：只向算法团队追问准确率。** 实际故障来自过期文档和权限过滤，模型替换并未消除问题。纠偏是沿入口、证据、计划、执行、业务状态逐层归因，再决定哪个负责人处理。

## 六、验收方法

请另一名读者拿责任书回答四个场景：检索来源失效、模型建议越权、写入结果未知、成本超预算。每个场景必须能找到判断依据、处理责任人、停止权限和对用户的表达。读者需要反复猜测，说明文档仍缺关键决策。

能力评估应看证据质量：一个研究结论是否可追溯，一个指标是否可复算，一个审批是否能绑定实际动作。作品集列出几十个产品名或提示词，不足以替代这些证据。可以记录学习自评，但不能把自评数字包装成正式测评结果。

## 七、工作坊

1. 选择一个真实工作任务；没有授权时只做虚构任务，不采集业务资料。
2. 填写结果责任书，把“助手更智能”改为可观察的任务结果。
3. 列出五个决策，分别确定提议、批准、执行和独立复核角色。
4. 用上述四类故障走查，补齐所有无人负责或无法停止的环节。
5. 写一段岗位说明，明确需要的机制理解与证据，不照抄技术关键词。

## 完成标准

交付一份结果责任书、一张能力证据表和至少一条架构决策记录。能区分任务完成与模型自报，能说明角色兼任的冲突，所有高风险动作都有负责人和停止条件。真实研究与测试未做时，产物必须明确标注未执行。
