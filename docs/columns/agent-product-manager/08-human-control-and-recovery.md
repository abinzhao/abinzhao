# 人工介入、权限与恢复：把动作控制在可承受范围

## 学习目标

本章将“人工确认一下”转成可执行控制。学完应能定义批准对象、有效条件与执行校验，解释超时为什么不能直接重试，区分取消、撤销和补偿，并写出另一名专员可以接手的恢复记录。

## 一、人工在环的价值与限制

Human in the Loop 指在任务过程中安排人工判断、批准或接管。它不是所有风险的自动解药。若界面不展示关键差异、用户没有时间或知识检查，审批会退化成习惯性点击。若执行器不核对批准内容，用户批准的安全动作仍可能被替换成危险动作。

[OpenAI 的 Agent Builder 安全建议](https://platform.openai.com/docs/guides/agent-builder-safety)包含审批、结构化边界和防止注入的措施，但不承诺绝对安全。[MCP 的规范和安全考虑](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)也强调连接与授权责任。产品因此要同时设计人的判断界面和应用的强制控制，不能只要求模型“遇到危险问用户”。

按动作代价和可逆性分级，比按功能名称分级更有用。检索公开资料、检索敏感资料、修改分类、发送外部消息和转账的风险不同。同一个工具可因目标对象不同而改变风险，不能仅因工具被标记为“安全”就一律免审批。

## 二、批准必须绑定精确动作

批准对象至少包含任务、用户、租户、工具、资源、变更前后值、预期版本、有效期限和执行次数。批准后参数、资源或版本变化，应重新评估或重新批准。仅保存“用户点过确认”，无法证明用户确认的是哪次动作。

应用还要在执行前检查当前权限。用户批准后离开角色，批准不能维持旧权限；工单被他人更新，旧批准不能覆盖新版本。这个问题常被称为检查与使用之间的状态变化，产品需要明确定义冲突提示与重新批准流程。

批准信息由可信应用产生并验证，不由模型生成。凭据不应显示给模型或写进聊天记录。[Anthropic Managed Agents 的实践](https://www.anthropic.com/engineering/managed-agents)展示凭据与执行环境分离的特定设计，可作架构参考，但不代表所有沙箱自动具备相同保障。

## 三、交付样例：审批契约

以下为教学工单写入规格；首版仍只读，此能力只有相关控制验证后才可开放。

| 字段 | 已填写样例 |
| --- | --- |
| 资源 | `TICKET-LAB-001`，当前租户 `tenant-lab` |
| 工具 | `apply_approved_ticket_patch`，仅内部字段修改 |
| 变更 | `category: unknown → policy-question` |
| 禁止字段 | 账户权限、退款金额、收件人、外发正文、人事结论 |
| 预期版本 | `rev-7`，执行前回读并比较 |
| 批准人 | 当前已验证专员，具有该字段的业务写权限 |
| 有效范围 | 单一任务、单一资源、单一变更；不得批准后追加字段 |
| 教学有效期 | 五分钟；实际有效期需按风险与操作耗时验证 |
| 幂等标识 | 应用生成 `action-lab-001`，同一动作重试复用 |
| 完成判定 | 实际回读字段与版本，并关联动作记录 |
| 审批界面 | 显示对象、前后差异、依据、影响和拒绝按钮 |

动作内容摘要或哈希可用于绑定变更，但产品需求应明确标准化、字段完整性和校验责任，不把“加一个哈希”当充分安全实现。界面显示的内容与执行器校验的内容必须一致。

## 四、幂等与未知结果

网络超时有两种可能：请求未到服务，或服务已提交但响应丢失。客户端只看到超时，不能知道哪种发生。此时显示“失败，请重新执行”会诱导重复写入，正确状态应是“结果未知，正在核对或需要接管”。

幂等用于让同一业务动作的重复请求不产生重复效果。它需要实际服务支持稳定标识、结果查询或相应业务机制；客户端自行保存一个字符串并不保证服务端幂等。产品要确认能力在哪一层成立，以及保留期限、重复参数冲突和重放规则。

任务完成最好通过可信业务状态确认，不只依赖工具返回“success”。回读也可能延迟或失败，因此要定义核对窗口和人工路径。不能通过不断重试掩盖状态未知，不能要求模型推断写入是否已发生。

### 失败恢复矩阵

| 事件 | 状态与用户说明 | 后续动作 |
| --- | --- | --- |
| 执行前校验失败 | 未执行，说明具体范围或版本冲突 | 修正规格，必要时重新批准 |
| 已明确拒绝 | 未执行，保留错误类型 | 不扩大权限；可人工处理 |
| 请求超时 | 结果未知，不宣布成功或失败 | 查询动作记录与资源状态 |
| 回读确认已提交 | 已完成，显示实际变更 | 不重复写入；记录核对依据 |
| 回读确认未提交 | 可重试但仍需有效批准 | 同一动作复用幂等标识 |
| 无法确认提交 | 待人工接管 | 冻结相关写入并交接 |
| 用户取消但请求已发出 | 停止后续步骤，既有动作仍待核对 | 查证副作用，不承诺撤销 |
| 参数变化或批准过期 | 原批准无效 | 新建议与重新批准 |

## 五、取消、撤销和补偿是三件事

取消通常停止尚未执行的工作；撤销试图恢复已有状态；补偿用新的业务动作处理既有影响。发送消息后无法保证收件人没看到，即使删除也不等于没发生。退款、权限变更等动作还可能需要独立审批，不能让 Agent 自己“反向操作”抵消。

部分成功的多步任务需要记录每步实际状态。先改分类再发送消息，第二步失败并不意味着第一步未发生。恢复时应从可信记录开始，决定继续、补偿或交接，不简单重跑整条链。教学案例不开放外发，但可以用此场景演练不可逆影响。

恢复设计还应考虑进程崩溃与会话结束。用户关闭页面后，运行状态不能只存模型上下文；下次打开要能看到任务、批准、已执行步骤和未知项。恢复不自动获得新的权限，原批准是否仍有效必须重新检查。

## 六、交付样例：人工交接单

```text
任务：TASK-LAB-01；资源：TICKET-LAB-001；动作：action-lab-001
用户目标：仅把分类改为 policy-question；不外发、不结案。
批准范围：category 字段，基于 rev-7；当前有效性需重新核对。
已确认：请求已发出；工具响应超时。
未确认：服务是否提交、资源当前版本、幂等记录是否存在。
暂停措施：冻结同任务后续写入，不创建新动作标识重复提交。
接管步骤：查询动作记录，回读工单；确认提交后结束，确认未提交才评估重试。
禁止推断：不得依据模型摘要或“应该没成功”判断结果。
证据状态：本单为教学模拟，真实工具和恢复流程未运行。
```

这份交接单让下一名专员知道不能做什么，也避免重新解释全部聊天。敏感原文和凭据不应为了“交接完整”加入其中。

## 七、失败案例与验收

**失败案例：批准一次，执行无限次。** 用户批准分类修改，Agent 后续继续修改优先级。根因是批准未绑定字段与执行次数。纠偏是在应用检查完整动作，变化后重新批准。

**失败案例：超时后生成新幂等标识。** 同一业务动作被服务视为两个请求，产生重复效果。纠偏是对同一动作复用标识并核对结果；新标识只能对应经明确区分的新动作。

**失败案例：人工总是点同意。** 审批文案只写“是否继续”，看不到差异与影响。纠偏是减少无价值审批，将需要判断的信息显著展示，并评测审批理解与错误发现，而非只看点击率。

验收要覆盖批准后权限撤销、资源版本变化、响应丢失、回读失败、重复点击、取消与进程恢复。所有用例先在授权测试环境进行，不能拿真实高风险业务试错。验收对象是实际状态与控制，不是模型有没有说“已暂停”。

## 八、工作坊

1. 填一份精确审批契约，圈出所有模型不得生成的批准字段。
2. 演练响应丢失，分别列已提交与未提交两种可能。
3. 用恢复矩阵走查取消、崩溃、重复请求和部分成功。
4. 写一份人工交接单，让陌生读者不看聊天也能安全接管。
5. 设计审批理解测试，检查用户是否识别了资源、变更和影响。

## 完成标准

交付审批契约、恢复矩阵、交接单和边界验收清单。能够区分未执行、已完成和未知；没有未知结果可以通过无条件重试跳过。取消不冒充撤销，凭据不进入模型上下文，所有未实现控制明确标注。
