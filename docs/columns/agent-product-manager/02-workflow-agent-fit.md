# Workflow、Agent 与适用性：控制权如何分配

## 学习目标

本章不按营销名称分类产品，而是检查“谁选择下一步”。学完应能画出控制循环，判断何时采用固定流程、受限 Agent 或人工操作，并为增加自治能力写出证据门槛。课程不认为所有任务都应改造成 Agent。

## 一、模型参与不等于拥有行动控制权

[Anthropic 在 2024 年的工程文章](https://www.anthropic.com/engineering/building-effective-agents)中，将预定义代码路径组织的系统称为 Workflow，将模型动态指导过程与工具使用的系统称为 Agent。这个区分强调控制方式，而非是否使用大模型。原文现在有工具生态更新提示，因此可以借用控制权概念，不能把旧示例接口当成当前实现标准。

固定流程可以是“输入校验 → 查询授权知识 → 生成草稿 → 人工确认”。模型负责生成文本，但不能自己决定访问任意系统。受限 Agent 则可能根据检索结果决定澄清、改写查询或读取更多证据；下一步由模型提出，应用仍负责校验是否允许。业务状态机控制写入和终止，不应交由模型自由定义。

“自治”也不是一个开关。目标设定、工具选择、工具参数、权限批准、执行和完成判定可以分别由用户、模型或应用负责。一个允许模型选择只读检索工具、但每次写入都需人工批准的系统，有局部自治能力，却不是完全自动代理。

## 二、控制循环及其停止条件

典型循环是：接收任务与边界，观察当前状态，提出下一步，校验行动，执行或请求批准，读取执行结果，再决定继续或停止。[OpenAI 工具调用文档](https://platform.openai.com/docs/guides/function-calling)说明模型调用建议与应用执行相分离；[Anthropic 2026 年 Managed Agents 实践](https://www.anthropic.com/engineering/managed-agents)展示了会话、Harness 与执行环境分离的具体产品设计。它们不提供通用成功率，但支持把运行控制与模型输出分开的思路。

停止条件至少覆盖成功、用户取消、缺少证据、权限不足、预算耗尽、工具故障和结果未知。没有停止条件的“不断尝试直到完成”，可能反复调用相同工具、扩大信息暴露，或者在已经成功写入后重复提交。

控制器还必须管理资源：允许哪些工具，每次能读取多少材料，最大行动次数和时间预算是什么。案例初始教学值可设为最多两次检索、总处理预算三十秒，超过后展示可接管结果。这是人为规格，不是模型最佳参数；实际限制要通过任务测试与成本分析重新确定。

## 三、适用性判断的五个问题

第一，路径能否可靠预定义。任务只有几个固定分支时，状态机通常更便于测试；任务需要根据未知信息探索时，才有增加动态规划的理由。第二，输出是否可验证。能核对权威证据、字段或真实状态的任务，比只能靠“感觉不错”判定的任务更容易建立闭环。

第三，错误代价是否可控制。不可逆财务动作、敏感权限和重大个人权益不应仅凭模型判断开放。第四，工具是否具备稳定契约。缺少身份、幂等、错误分类或回读能力时，增加智能规划无法弥补执行缺口。第五，增益是否超过额外复杂度。新增循环、记忆和协调会增加延迟、失败面、评测与运维负担。

| 任务特征 | 候选设计 | 主要验收焦点 |
| --- | --- | --- |
| 固定字段与固定规则 | 表单、规则引擎或确定性流程 | 规则覆盖、校验与错误提示 |
| 一次检索即可形成草稿 | 检索加生成的固定流程 | 证据覆盖、权限和拒答 |
| 需澄清或有限检索探索 | 工具白名单内的受限循环 | 停止条件、重复行动与预算 |
| 跨系统写入且结果可能未知 | 受控编排加审批状态机 | 幂等、回读、交接与补偿 |
| 多个可独立验证的子任务 | 先评估并行工具或分工 | 合并标准、冲突与协调成本 |

不要将这张表当成自动评分器。可预测性与代价需要真实任务证据；没有数据时，记录“待验证”，选择能保留人工接管的较小范围。

## 四、交付样例：适用性决策记录

以下是“澄明服务台”的教学设计，未经过真实任务或模型运行验证。

| 字段 | 已填写样例 |
| --- | --- |
| 任务 | 专员查询 `KB-LAB-001` 的规则并生成答复草稿 |
| 固定边界 | 仅 `tenant-lab`、有效知识、只读工具、不自动发送 |
| 不确定部分 | 用户可能缺少问题发生时间，检索可能返回多个适用版本 |
| 方案 A | 表单确定时间和类型，固定检索，再生成草稿 |
| 方案 B | 模型在两次检索预算内选择澄清或改写查询 |
| 方案 C | 多 Agent 分别研究政策、风险和答复，再合并 |
| 当前选择 | 先实施方案 A 的规格与夹具，保留方案 B 对照 |
| 选择原因 | 首版任务路径可描述，尚无证据证明动态循环有额外价值 |
| 暂不选 C | 缺少独立子任务、合并标准和收益证据，协调复杂度无依据 |
| 升级门槛 | A 的明确失败集中在有限探索，B 在同任务配对评测中改善且不破坏护栏 |
| 降级条件 | 循环重复、越权尝试、延迟或预算超限，回到固定流程和人工 |

关键推理是先寻找方案 A 的失效原因。如果失败来自知识库缺规则，方案 B 多检索一次也不会获得不存在的证据；如果失败来自授权过滤错误，动态循环反而可能扩大风险。只有失败确实与固定路径表达能力有关，增加规划权才有因果依据。

## 五、多 Agent 不是天然更可靠

多个角色对同一材料“讨论”，不等于获得独立证据。它们可能共享同一缺失知识、同一模型偏差和同一错误假设，最后一致输出错误答案。增加一个“审查 Agent”不能替代真实状态判定，也不能自动生成授权。

有意义的分工应具备可分离输入、明确产物、可独立验证和受控合并。例如独立读取两个已授权系统的只读状态，可以先并行确定性工具，再由单一合并规则处理冲突。若各子任务争抢同一工单写权限，协调和回滚难度上升，应先定义单一执行所有者。

产品评审要比较最小替代方案：单次调用、固定路由、并行工具、单 Agent 循环和多 Agent。比较不仅看答案，还看调用次数、证据可追溯性、错误传播、总延迟及每个任务的人工复核成本。没有对照结果，不能把架构复杂度当产品创新指标。

## 六、失败案例与验收

**失败案例：检索循环越跑越远。** 用户问已发布规则，系统首次未找到，自动搜索相邻租户和公共网页，再用过期资料回答。根因是搜索范围没有硬边界，缺失证据被当成扩大权限的理由。纠偏是先校验租户和数据范围，明确“找不到”是合法终态。

**失败案例：把步骤数限制当安全控制。** 即使只允许一步，一次越权写入仍可产生严重后果。预算控制解决资源消耗，授权控制解决行动是否合法，两者不能互相替代。

验收时用六张任务卡走查：固定顺利任务、缺时间、来源冲突、无证据、工具失败、用户取消。逐张记录下一步由谁决定、哪些行动被拒绝、最终状态是什么。若模型输出不同但都遵守同一契约，可以接受；若输出格式一致却执行越权，不可接受。

## 七、工作坊

1. 为一个任务画出不使用模型的基线流程，先找无法可靠预定义的环节。
2. 将目标、规划、参数、批准、执行、完成判定分别分配给角色。
3. 写三个方案，不得只比较两种模型而忽略规则或人工替代。
4. 为动态循环补齐停止、预算、重复请求与异常终态。
5. 设计一组可推翻当前选择的对照任务，保留失败轨迹。

## 完成标准

交付控制权表、六个场景走查和一份适用性决策记录。能够解释选择 Agent 的新增价值与新增风险；没有收益证据时明确保留较简单方案。不得将教学预算、多 Agent 分工或厂商产品实践写成通用行业标准。
