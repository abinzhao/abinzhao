# 数据体系与产品指标：先定义分母，再讨论提升

## 学习目标

本章训练把“效果很好”转为可复算指标。学完应能定义任务、运行与动作标识，区分系统输出和业务结果，处理退出、超时和缺失，并在不默认收集原始内容的前提下设计数据字典。埋点存在不等于数据可信。

## 一、对象层次决定指标口径

一个用户目标对应任务，一个任务可能有多次运行，一次运行可能提出多个工具动作。将所有调用都算作任务，会让重试较多的方案获得虚假的高使用量；只计算最终成功运行，会隐藏第一次失败与用户等待。

[Anthropic 的评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)区分 Task、Trial、Grader、Trace 和 Outcome。产品分析也应保留相应层次：用户任务、运行尝试、执行动作与实际结果。业务结果要来自可信系统或独立判定，而不是模型写出的结束句。

教学案例中，`TASK-LAB-01` 是一次查证目标，`RUN-LAB-01` 是一次具体运行，`ACTION-LAB-01` 是一个工具动作。标识应由应用生成，模型不能随意覆盖。重试创建新运行时仍关联原任务；同一业务写入的幂等标识保持稳定。

## 二、交付样例：最小数据字典

下表是教学规格，未部署埋点，没有真实任务数据。

| 字段 | 定义与来源 | 限制 |
| --- | --- | --- |
| `task_id` | 应用生成的任务标识 | 不编码姓名、工单正文或账户 |
| `run_id` | 本次尝试标识，关联任务 | 不将重试当新用户价值 |
| `action_id` | 实际动作与幂等关联 | 提议和执行分开记录 |
| `variant_id` | 经批准的方案版本 | 包含模型、提示、检索与工具配置引用 |
| `task_type` | 受控枚举的任务类型 | 不用原始问题作为分类值 |
| `terminal_state` | 草稿就绪、拒答、取消、失败、未知等 | 来源为执行状态，不是模型自报 |
| `evidence_status` | 独立检查的支撑与有效性状态 | 缺判定必须显式表示 |
| `duration_ms` | 起止定义一致的耗时 | 区分生成、复核、等待和完整任务 |
| `usage_cost` | 可归因调用及资源账目 | 价格时间、币种和共享分摊需记录 |
| `handoff_reason` | 权限、无证据、冲突、未知、故障等 | 不默认保存敏感原文 |
| `feedback_state` | 好评、差评、未反馈、撤回 | 未反馈不等于满意 |

标识本身也可能与个人关联，因此“去掉姓名”不能自动宣称匿名。应按访问、关联和再识别风险管理；实际保留期限与法律基础由治理角色确定。

## 三、事件契约与任务漏斗

建议将事件分成用户入口、任务开始、证据结果、草稿结果、审批、执行、核对、终态和反馈。事件字段需要版本，避免新旧客户端使用同名事件但不同含义。事件发送失败时也应能识别数据缺口，而不是默默当用户没做。

```json
{
  "event_name": "task_terminal",
  "event_version": 1,
  "task_id": "TASK-LAB-01",
  "run_id": "RUN-LAB-01",
  "variant_id": "variant-readonly-lab",
  "task_type": "policy-question",
  "terminal_state": "insufficient_evidence",
  "outcome_source": "application_state",
  "content_collected": false
}
```

这是数据契约示例，不是已发生事件。它不包含原始问题和完整答案，也不意味着所有诊断都不需要内容。若调试确需内容，应建立单独授权、最小取样、脱敏与受控访问流程，不能默认扩大遥测范围。

任务漏斗可以是“具备资格 → 明确曝光 → 启动 → 获得可用草稿 → 复核后采用 → 业务任务完成”。每一层要解释资格和完成，不把点击次数当独立用户，不把草稿采用当最终服务问题解决。

## 四、指标说明：分母与缺失

| 指标 | 分子 / 分母 | 解释与限制 |
| --- | --- | --- |
| 合格任务完成率 | 达到任务标准的任务 / 所有符合资格并启动的任务 | 取消、超时、未知按预先规则保留，不能只看有答案任务 |
| 证据支撑率 | 通过独立检查的关键主张 / 应检查主张 | 同时报未检查数量，不能把未评当通过 |
| 草稿采用率 | 经复核采用的草稿任务 / 草稿就绪任务 | 需说明采用事件，不等于答案正确 |
| 人工接管率 | 进入接管的任务 / 启动任务 | 接管可能是正确安全行为，不能一律压低 |
| 首次运行成功率 | 首次运行达到标准的任务 / 启动任务 | 与允许重试后的最终完成率分开 |
| 每完成任务成本 | 全部相关任务成本 / 合格完成任务 | 包含失败与重试，不只计成功调用 |
| 未知结果率 | 终态无法核对的任务 / 启动任务 | 需要值守处理，不可归为普通失败后忽略 |

“拒答率越低越好”尤其危险。对越权、无证据和冲突任务，拒答可能是正确结果；对本应支持的任务，过度拒答才是质量损失。指标需要按任务类型和正确终态分层，避免优化一个数字损害边界。

缺失要分类为事件丢失、评分未完成、用户退出、工具超时或结果未知。无法观测完成状态时，不能擅自按成功计算；也不必将所有缺失都当业务失败，应按预注册口径提供保守主指标和缺失说明。第十章将用夹具展示排除缺失如何制造虚假提升。

## 五、耗时、分位数与业务价值

首字耗时衡量感知等待，完整草稿耗时衡量生成结果，复核后任务耗时更接近价值。人工主动时间与审批等待不同；并行处理时，简单加总会重复计时。时间研究应说明起止、暂停、后台时间和多人交接。

平均耗时可能被少数长任务主导，中位数会隐藏尾部。可同时报告任务类型、分位数、样本量和超时比例；分位数需要足够数据，不能凭极小样本宣称稳定尾部表现。对超时任务，只统计已完成任务耗时会产生选择偏差，应同时报告截止时间和未完成数量。

指标之间还可能冲突：缩短答案会降低耗时，却遗漏关键条件；降低接管率会迫使系统在无证据时回答。产品需要主指标、质量护栏、权限护栏和预算护栏，并记录哪个护栏可以直接阻断扩量。

## 六、数据质量与归因

发布前检查标识唯一、事件顺序、重复发送、时钟偏差、跨版本兼容和终态一致性。任务状态应与执行记录对账；写入成功事件必须能关联真实业务状态，不以模型输出事件代替。

模型、提示、知识版本、检索策略和工具变化都可能影响结果。只记录模型名，无法归因改动。应保存配置引用而非秘密内容，保留评测环境和知识快照的合法标识。数据字典变化也属于产品变更，需要同步指标定义。

## 七、失败案例与验收

**失败案例：排除没有评分的任务。** 难任务更容易超时并缺评分，剩下的简单任务显示高完成率。纠偏是保留原始任务分母，单独报告缺失原因，按预定规则做敏感性分析。

**失败案例：好评率作为准确率。** 用户可能因为语言礼貌而点赞，错误却未被发现。纠偏是将反馈与独立正确性判定分开，同时保留未反馈状态。

**失败案例：日志收集完整聊天。** 团队为了诊断将问题、答案和工具返回全部上传，超出原先隐私承诺。纠偏是最小事件默认、内容诊断单独授权，并检查实际网络与保存行为。

验收使用手工教学事件走查：重试、重复事件、取消、超时、无证据、未知写入和延迟反馈。让不同读者按同一数据字典算指标，分母或结果不同则说明定义仍不明确。

## 八、工作坊

1. 建立任务、运行、动作三级字典，说明标识生成与关联。
2. 定义一个主指标和四类护栏，写清分子、分母与缺失。
3. 构造只用于口径检查的手工事件，不声称真实使用数据。
4. 让另一名读者复算，检查重复、超时与反馈缺失。
5. 画数据去向和保留表，删除不必要的内容字段。

## 完成标准

交付数据字典、事件契约、指标说明及数据质量清单。任何完成率都有可解释分母，任何成本都有失败任务归属，反馈不冒充正确性。实际埋点、内容流向和业务对账未验证时必须标注，不宣称已经建立可信数据平台。
