# LLM、RAG 与知识边界：答案如何获得证据

## 学习目标

本章帮助产品经理把“基于知识回答”拆成可验收环节。学完应能解释检索与生成的区别，区分引用存在、引用支撑和事实有效性，定义版本、权限、冲突及缺失证据的行为，不将长上下文或 RAG 当成正确性保证。

## 一、生成与检索解决不同问题

语言模型根据上下文生成输出，不是业务数据库的事实查询接口。模型可能写出连贯解释，但连贯不代表当前规则有效。检索增强生成，即 RAG，将外部材料检索后提供给模型；它增加可用证据，不自动保证材料完整、适用、授权或被正确解释。

一条回答链可以包含文档入库、内容切分、索引、查询改写、检索、重排、上下文组装、生成和证据验证。产品不需要规定某种向量数据库，却需要明确每个环节的责任与失败类型。检索没找到是覆盖问题，找到错误版本是治理问题，生成误读条件是解释问题，引用越权文档是授权问题。

[Anthropic 上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)讨论检索、摘要和有限上下文的管理。[OpenAI 评测建议](https://platform.openai.com/docs/guides/evaluation-best-practices)主张使用具体任务和持续评测。这两项资料支持分层设计与验收，但不能证明任何默认检索参数或模型具有指定正确率。

## 二、证据的四层质量

第一层是可解析：引用指向存在的文档与段落。第二层是可访问：当前用户有权查看这份证据。第三层是可支撑：被引用段落确实支持相应结论，包括例外和条件。第四层是有效：文档版本、发生时间、地域、产品和用户类别符合任务。

例如，引用 `KB-LAB-001` 的有效段落仍可能失败：该段落只允许“请求补充说明”，草稿却断言“可直接结案”。引用编号合法并不能证明推论合法。评测应将每个关键结论对应到证据，而不是只统计回答有几个引用。

证据冲突也不能交给语言流畅度解决。新旧版本冲突时按明确的有效期与批准信息选择；两个同级有效来源冲突时展示冲突并转知识负责人，不让模型自行宣布谁更权威。没有权威来源时，可以解释缺口和给出下一步，但不能补造政策。

## 三、检索边界与上下文预算

关键词检索对明确编号或术语可能有效，语义检索有助于处理表达变化；混合方式和重排是候选策略，不是必选组合。选择依据应是任务集上的覆盖、证据精度、延迟与治理成本。产品要写清“找什么、不能找什么、怎样确认找到”，不要用“上向量库”替代需求。

权限过滤应进入检索和证据读取链路，不能只在最终回答时提醒“请勿泄露”。检索结果中的标题、摘要、数量也可能泄露信息。应用须基于已验证身份与租户决定范围，不能让模型给出的 `tenant_id` 覆盖当前会话。

长上下文提供更多材料，却可能增加无关信息、冲突和阅读成本。摘要降低体积，但可能遗漏限制条件。产品应规定保留原始证据定位，摘要不得替代批准版本；若上下文预算无法容纳关键条件，应减少任务范围或分步读取，而不是截断后仍自信回答。

## 四、交付样例：知识回答契约

以下政策与标识均为教学样例，不代表真实企业规则。

| 字段 | 已填写样例 |
| --- | --- |
| 文档 | `KB-LAB-001`，版本 `v3`，批准角色为知识负责人 |
| 租户和范围 | `tenant-lab` 内部服务台，角色 `agent-reader` |
| 教学规则 | 信息缺失时请求补充；证据冲突时转负责人；不自动结案 |
| 必需元数据 | 文档标识、版本、批准状态、有效起止、范围、段落定位 |
| 查询条件 | 当前身份与租户、问题类别、发生时间；缺时间先澄清 |
| 答复结构 | 结论草稿、适用条件、证据定位、未解决问题、下一步 |
| 拒答条件 | 无授权证据、仅有过期材料、同级来源冲突、任务超范围 |
| 引用规则 | 关键政策结论逐项有支撑；引用不可访问时不显示敏感摘要 |
| 更新要求 | 撤销来源后停止作为有效证据；索引更新状态可查询 |
| 责任 | 业务批准真相，工程落实过滤，产品定义体验与验收 |

### 可替换的输出示例

```text
任务：TASK-LAB-01
草稿：当前信息不足以确认处理条件，建议先补充问题发生时间。
依据：KB-LAB-001 / v3 / paragraph-2（教学规则：缺信息先补充）
适用范围：tenant-lab 内部咨询；来源批准状态须由系统校验。
未解决项：发生时间未提供，不能确认有效政策版本。
下一步：请专员补充时间后重新查询；此草稿尚未发送或结案。
```

这个示例把“缺信息”转为可操作状态，而不是用“可能”“大概”掩盖证据缺口。真实实现还要确保引用确实解析到正文；展示文本本身不能证明后台已校验。

## 五、知识治理是产品生命周期的一部分

知识不是一次导入后永不变化的附件。需要定义谁能发布、谁批准、何时生效、怎样撤销、索引何时更新、旧答复怎样标记。若政策在任务进行中失效，系统应在实际动作前重新检查，而不是因为生成时有效就永久有效。

删除也有多个位置：源文档、索引、摘要、检索缓存和会话保存。只删原始文件，旧缓存仍可能继续供模型读取。删除策略要和第六章记忆生命周期及第九章数据事件协同；产品不能承诺“立即完全删除”，除非目标环境有可验证实现与相应合同边界。

知识运营可设“未覆盖任务队列”，由业务人员确认该任务是否应被覆盖，再更新来源。不能直接把低评分答案作为新知识，否则可能将幻觉写回知识库，形成自我强化。知识更新后重跑相关回归任务，保留旧版本用于合法审计，但审计版本不得继续参与常规回答。

## 六、验收与失败案例

评测至少分开检查检索覆盖、证据有效、解释正确、拒答合理和用户复核。为每张任务卡列允许来源、必须条件、不可出现结论及判定方式。某项结论通过，不自动意味着整个任务通过；使用者能够点开引用，也不意味着引用支持整句答案。

**失败案例：合法编号造成错误安全感。** 系统给每个答案附合法引用，但引用只谈一般流程，答案新增例外。纠偏是将答案拆为可核对主张，由人工或经校准的评分器逐项检查支撑。

**失败案例：权限只过滤正文。** 未授权用户看不到全文，却看到检索标题与摘要。纠偏是把所有返回字段纳入权限范围，并测试空结果、统计数量和日志，避免侧信道泄露。

**失败案例：改模型解决过期知识。** 新模型更善于解释旧文档，却仍依据已经失效的政策。纠偏是修复元数据与更新链路，再测模型解释能力。

## 七、工作坊

1. 写三份教学知识，分别为有效、过期和相互冲突版本。
2. 填知识回答契约，明确权限、有效期和缺失信息行为。
3. 设计六张任务卡，覆盖正常、无证据、过期、冲突、越权和误引用。
4. 手动走查每条结论与证据，记录引用存在但不支撑的情况。
5. 模拟撤销文档，列出源、索引、缓存和会话需要怎样处理。

## 完成标准

交付知识回答契约、版本治理表和六张验收任务卡。能够分层定位错误，所有关键结论有可检查证据，缺失与冲突有明确终态。教学知识不能冒充真实政策；未运行检索或模型时不得宣称检索召回或回答质量达标。
