# 用户研究与任务发现：从工作证据识别机会

## 学习目标

本章训练从“大家都想要 AI”回到真实工作。学完应能制定研究计划，观察任务而不只收集偏好，分离事实与解释，并写出带异常、授权和验收条件的任务卡。没有数据访问权时，只能演练研究方法，不能补写虚构访谈结果。

## 一、研究对象是任务，不是对 AI 的态度

“你是否希望有智能助手”容易获得礼貌性赞同，却没有说明问题发生频率、影响和现有替代方案。更有效的起点是最近一次具体事件：“当时收到什么请求”“你先查哪里”“为什么切换系统”“哪一步需要其他人确认”。如果受访者只能描述理想流程，就将其标为回忆或规则陈述，而不是现场观察。

任务还要包含触发、目标和结束状态。用户在知识库输入关键词只是一个动作，真正任务可能是确定规则适用条件并向请求者解释。只优化搜索速度，有可能把节省的时间转移到复核答案和修正错误上。因此需要从触发到业务完成观察整条路径，而非只记录模型能参与的那一段。

产品研究的方法选择属于教学建议。[GitLab 的产品岗位实践](https://handbook.gitlab.com/job-families/product/product-manager/)支持持续理解用户与问题，但不是本章样本配额的依据；[Anthropic 评测实践](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)说明任务与实际结果需要明确，帮助把研究产物转化为后续评测对象。

## 二、授权取样与研究设计

开展研究前先明确允许采集什么。访谈同意不代表可以录下真实工单中的个人信息，部门负责人允许观察也不代表可以向外部模型上传内容。研究计划应列数据类别、目的、访问人、保存位置、期限和删除路径。必要时采用去标识化记录或在受控环境中现场查看，不复制原文。

抽样应覆盖任务与风险差异，而不是只找积极使用 AI 的同事。考虑新人和熟练专员、常见和例外请求、白天和交接时段、不同知识领域。定性研究适合发现机制，不能由几次访谈估算整个组织的发生率。达到某个样本数量也不自动证明“饱和”，需要说明新增材料是否还改变任务分类及例外理解。

### 交付样例：研究计划

以下为虚构案例计划，全部研究活动未执行。

| 字段 | 已填写样例 |
| --- | --- |
| 研究问题 | 专员在哪些条件下找不到有效政策，失败如何影响答复与交接 |
| 目标对象 | `tenant-lab` 新人与熟练专员，覆盖日常请求和异常请求 |
| 方法 | 情境观察、最近事件访谈、授权流程文档核对 |
| 初始招募 | 计划覆盖两类经验水平与两类任务；不设代表总体的统计结论 |
| 采集内容 | 去标识化步骤、系统切换原因、等待原因、证据核对方法 |
| 不采集内容 | 请求者身份、账户、完整工单原文、秘密政策和凭据 |
| 同意与撤回 | 说明研究目的；可停止观察，并按批准规则撤回未匿名材料 |
| 保存安排 | 研究负责人受控存储；教学建议三十天后复查是否仍必要 |
| 分析方式 | 按任务机制编码，保留反例与研究者解释分开记录 |
| 停止条件 | 授权不清、出现敏感信息、观察影响真实服务时立即暂停 |

这里的期限与招募组合是教学起点，不是法规标准。实际保存期限必须与目的、组织政策和法务判断一致。

## 三、怎样做一次不诱导的访谈

开场先解释不是考核个人效率，而是理解任务。随后按事件顺序询问：触发是什么，输入缺了什么，如何判断来源可信，何时向他人求助，怎样知道工作已完成。不要先演示产品再询问痛点，否则受访者可能围绕演示功能重新组织回答。

对一句“很麻烦”，追问具体成本：“最近一次需要重复哪个动作”“是否等待批准”“如果不做会发生什么”。对一句“助手应该自动处理”，追问授权：“谁承担错误”“哪些操作你仍要检查”“不可逆操作怎样暂停”。这些问题让需求从功能愿望变成结果与控制条件。

观察时分别记录动作、原话、时间来源和解释。例如“打开第二个知识页”是观察，“因为第一个页面过期”需要受访者说明或版本证据，“知识治理差”则是研究者解释。不要把解释直接记入原话栏，更不能为作品集生成自然流畅的访谈引语。

## 四、任务拆解与证据账本

将一条任务拆成触发、输入、判断、行动、等待、交接和结果。等待批准与实际阅读耗时不同；系统切换可能是权限原因，也可能是知识分类不清。需要保留因果链，避免用“点击多”直接推导“应该用 Agent”。

| 证据类型 | 可以支持的判断 | 不可以支持的判断 |
| --- | --- | --- |
| 现场观察 | 此任务在此环境中的实际路径 | 总体平均耗时和发生率 |
| 最近事件回忆 | 用户的解释、决策动机和感受 | 精确时长与完整执行顺序 |
| 授权日志 | 已记录的操作及时间关系 | 没有记录的认知工作 |
| 政策文档 | 规定应如何处理 | 员工实际一直如此处理 |
| 产品反馈 | 有反馈者的经历与诉求 | 所有未反馈者的满意程度 |

对每条结论建立证据编号和反例。例如“需要更好的证据展示”可以由观察与政策核对共同支持，但必须检查熟练用户是否已经有快捷方法。如果熟练用户无需工具即可解决，产品可能应优先服务新人，而不是全员扩量。

## 五、交付样例：可进入规格的任务卡

这是从教学场景推导的规格示例，不是研究发现。

| 字段 | 已填写样例 |
| --- | --- |
| 任务编号 | `TASK-LAB-01` |
| 触发与目标 | 专员收到规则咨询，需形成可核对的内部答复草稿 |
| 必需输入 | 问题类别、发生时间、当前租户与用户权限 |
| 当前基线 | 手动搜索知识，检查版本，复制依据并编辑草稿 |
| 关键判断 | 来源是否有效、规则是否适用、证据是否冲突 |
| 可辅助动作 | 搜索授权知识、整理条件、生成带引用草稿 |
| 不可代替判断 | 批准政策变更、授权外发、决定重大个人权益 |
| 例外路径 | 缺时间先澄清；无证据说明缺口；冲突提交知识负责人 |
| 完成状态 | 草稿与证据可供专员检查；不将生成视为工单结案 |
| 价值假设 | 可能减少查找和核对负担，需要真实研究及对照测量 |
| 证据与缺口 | 仅教学设计；访谈、日志、任务频率和耗时均未取得 |

任务卡的边界使后续评测能构造正常、缺失、冲突和越权场景。不能将“能够生成文本”作为入选理由，也不能将没有证据的高频描述用于收入测算。

## 六、失败案例与验收

**失败案例：只访谈热情用户。** 研究得到“大家愿意用”，试用时却发现业务负责人不允许上传资料。根因是没有覆盖授权角色与反对者。纠偏是把批准、使用、付款和承受风险的角色分别列出。

**失败案例：把耗时记忆当测量。** 用户说“每次大概半小时”，团队据此乘工单数量计算收益。回忆可能包含等待、其他任务或罕见事件。纠偏是把该数字标为估计，设计授权时间研究，拆分主动时间、等待时间与复核时间。

验收研究报告时，随机挑一条结论，要求找到原始证据、分析过程、反例和未确认项。再反向挑一个记录，检查是否被过度概括。报告可以得出“证据不足以进入自动写入”，这不是研究失败，而是有效决策。

## 七、工作坊

1. 写一份研究计划，先完成授权和不采集清单。
2. 设计八个事件型问题，其中至少两个探索不使用产品的理由。
3. 用虚构任务演练观察记录，严格区分动作、原话和解释。
4. 形成两张任务卡：一张值得进一步验证，一张当前不宜自动化。
5. 为每个价值判断标注证据等级，缺数据处写待确认，不填数字。

## 完成标准

交付研究计划、访谈提纲、记录结构、证据账本和两张任务卡。能说明抽样限制、反例、数据授权及结论强度；研究未执行时，所有产物保持计划或教学示例身份。下一步产品定位只能使用实际取得的证据，不能把计划当发现。
