# 上线、运维与持续改进：让受控任务长期可用

## 学习目标

本章把“模型接通了”变成可值守的产品运行。学完应能写上线清单、服务目标与告警动作，组织事故沟通和恢复，管理知识与配置变化，并判断反馈是否真正闭环。

## 一、Agent 发布不是只发布应用代码

模型、提示、路由、知识快照、工具定义、权限、记忆策略、评分器和界面一起决定行为。只记录代码提交无法还原为什么昨天回答正确、今天答错。外部模型和服务可能变化，不能假定固定应用版本就完全可复现。

发布单应记录每项版本、实际账号与区域、能力开关、预算和回退对象。若供应商不能固定精确模型快照，应明确这种限制，并通过持续抽样监测行为漂移。不可复现不是不用记录的理由。

[OpenAI 持续评测建议](https://platform.openai.com/docs/guides/evaluation-best-practices)与 [Anthropic Agent 评测文章](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)支持任务特定回归和实际结果检查。它们不提供所有产品通用的 SLO、事故等级或上线成功率，以下为教学运行设计。

## 二、交付样例：上线清单

教学发布 `RELEASE-LAB-READONLY-01` 当前状态为未发布。勾选必须附证据，不能只签“已确认”。

| 检查项 | 放行所需证据与责任 |
| --- | --- |
| 范围 | 业务确认仅政策草稿，退款、外发、人事决定明确排除 |
| 知识 | 责任人签认有效版本、权限、生效时间与更新路径 |
| 行为 | 正常、缺条件、无证据、冲突、拒绝和故障任务报告 |
| 安全 | 模型外租户、工具、字段和网络边界的授权测试 |
| 隐私 | 实际接收方、日志、保留、删除和地区的审查记录 |
| 配置 | 模型、提示、工具、知识、路由、评分器与预算版本 |
| 容量 | 目标并发的排队、限流、延迟、费用和失败回退检查 |
| 体验 | 关键状态、证据、人工入口、键盘与目标设备检查 |
| 运维 | 告警到责任人、停能力开关、手动处理与事故演练 |
| 法务与采购 | 适用义务、合同和供应限制无未解决阻断项 |
| 发布方式 | 授权小范围、观察窗口、扩量与停止条件 |

影子运行也会处理数据、调用工具和产生费用，必须先授权；“用户看不到”不等于没有风险。首版影子模式只读，不允许借测试名义执行真实写入。小流量同样不能放松高影响控制。

## 三、SLO 同时需要口径和响应

SLI 是可计算的指标，SLO 是目标，SLA 通常涉及外部服务承诺，不能互换。HTTP 成功、模型返回和业务正确完成也是不同层。

教学设计示例：只读任务进入可执行状态后，滚动二十八天内至少 99% 在三十秒内产生明确技术终态。这里的终态可为草稿可用、需要补充、证据不足或明确故障；它衡量处理及时性，不证明答案质量。参数只是待验证目标，不是测得性能。

| 指标 | 分子、分母与解释 |
| --- | --- |
| 处理及时性 | 截止时间内终态数 / 进入可执行状态任务数；超时仍在分母 |
| 正确完成 | 按预定规则计为通过的任务 / 全部合格且已启动任务；取消、超时、未知保留，未评另报 |
| 授权边界 | 确认越权或泄露事件、受影响资源；不被及时性平均掩盖 |
| 延迟分布 | 首反馈、可用草稿、完整任务各自的 P50、P95 |
| 人工负担 | 检查、返工、接管耗时与任务总耗时 |
| 成本 | 全部任务支出、成功任务分摊和租户预算使用 |

等待用户补充不纳入这个技术处理段，但仍需报告完整任务历时与放弃；若用暂停时钟优化 SLI 而隐藏真实等待，指标就失去产品意义。错误拒绝可能按时，却在质量指标失败。

99% 的教学目标意味着允许的及时性失败占比为 1%，可形成相应错误预算讨论。预算消耗快时暂停无关发布、优先恢复可靠性，不是允许把泄露算进这 1%。目标需根据业务后果、容量和成本协商，没有真实测量前不得作为对外 SLA。

## 四、告警必须对应可执行动作

只告知“模型变差”难以处置。告警应有对象、影响、窗口、触发条件、证据链接、负责人和首个动作。阈值要根据实际基线校准，避免每次小波动都通知全员；安全硬边界则不应被普通噪声过滤掩盖。

| 告警情形 | 首个响应 | 禁止动作 |
| --- | --- | --- |
| 知识版本过期 | 停用相关来源，说明证据暂不可用 | 沿用旧政策并隐藏日期 |
| 工具限流或故障 | 限制并发、明确失败、提供人工路径 | 无限重试或扩大凭据 |
| 质量抽样异常 | 冻结扩量，核对评分与版本 | 放宽量表使看板恢复 |
| 租户预算接近上限 | 按已声明规则限制或请求确认 | 静默产生超额账单 |
| 确认越权或泄露 | 停相关能力、隔离影响、启动事故流程 | 只改提示继续运行 |
| 写入结果未知 | 冻结后续写入、核对动作与业务状态 | 新建动作标识重发 |

告警缺失也要测试：事件被丢弃、负责人离岗、供应商通知未订阅，可能让产品长期带错运行。演练包含通知到达和处理闭环，不只检查看板有红色图标。

## 五、事故处理和回退的不同层

教学分级可把泄露、越权或不可控副作用列为最高优先级，把大范围不可用列为紧急，把局部质量下降列为限范围处理。具体编号、时限和责任由组织确定，不包装成统一行业标准。

事故流程包括发现、止损、界定影响、证据保存、沟通、恢复和复盘。保存最小必要记录，受限查看敏感证据，不能为了排障把全部提示和工单复制到公共群。法定或合同通知条件由专业负责人判断，不能等待统计显著性。

停能力、回滚配置、回滚知识和恢复业务状态不是同一操作。关闭写入阻止未来动作，不撤销已提交变更；回退模型不消除已泄露内容；知识回滚可能重新引入过期规则。因此恢复从实际状态和有效版本开始，而非一句“已回滚所以安全”。

回退路径自身需验收。新旧字段、批准格式、记忆结构或工具契约不兼容时，旧版本可能无法理解新任务。未知结果保留人工接管，不因回滚清空动作记录。

## 六、交付样例：运行手册条目

```text
事件：TASK-LAB-01 的分类写入超时。此条用于后续受限写入演练。
范围：tenant-lab / TICKET-LAB-001 / action-lab-001。
先做：冻结同任务后续写入，用户看到“结果待核对”，不宣布失败。
核对：执行记录、幂等结果、工单字段与版本；仅授权人员读取。
若已提交：显示实际变更并结束，不重复写入。
若确认未提交：重新核对权限、批准有效期与版本后才评估重试。
若仍未知：交接业务专员与执行服务负责人，保持写入冻结。
沟通：已确认事实、未知项、当前限制、下一次更新安排。
恢复：业务状态可解释、相关边界回归通过、负责人同意才解除限制。
证据状态：教学模拟；未运行真实服务、告警或恢复流程。
```

运行手册还要明确谁能停能力、谁确认业务状态、谁批准恢复。产品经理负责用户影响与决策协调，不应替代工程签署技术安全结论，也不能把全部责任转给用户“自行判断”。

## 七、知识更新和反馈闭环

知识更新应有提出、审核、生效、索引、缓存失效、回归与发布记录。原始文档更新后检索索引可能仍旧；索引正确但缓存旧，同样会输出旧答案。监测应覆盖完整链路与权限撤销。

冲突政策需要业务裁决，不让模型根据发布时间或措辞自行决定。涉及重要条件的更新应加入风险回归集；重复访问保留评测集的规则要记录，避免开发和发布逐步污染评测。

反馈闭环是问题被分类、确定责任、处置、验收并向有授权的反馈人说明状态。标记“已收到”或直接加入训练数据不算闭环。数据是否可用于改进、需否脱敏、保存多久，先遵守授权与政策。

可按检索缺证据、政策解释、工具参数、权限、延迟、恢复和交互理解分类。每项关联版本、严重度与任务结果，不强制存完整原文。候选修复先在开发集验证，再按变更风险做回归与小范围检查，不把生产用户当无边界试验集。

## 八、失败案例、工作坊与完成标准

**失败案例：接口正常就宣布产品健康。** 模型持续返回错误政策但监控全绿。纠偏是技术可用性、任务质量和知识有效性分别监测。

**失败案例：回滚后删除未知动作。** 团队丢失已提交状态，恢复时重复写入。纠偏是保留动作与核对记录，配置回退不破坏业务事实。

工作坊交付上线清单、指标定义、告警矩阵、运行手册和知识更新流程。用知识过期、限流、质量异常、越权、负责人未收到通知和结果未知六种情形做桌面演练，记录谁决定、凭什么恢复、用户看到什么。

完成标准是每个重要告警都有动作和责任，回退不被说成撤销，未评与未知仍可追踪。文档与桌面演练只能证明方案可讨论；真实 SLO、容量、安全、通知到达和恢复必须在授权目标环境验证，本章未上线或值守生产系统。
